# CLAUDE.md | Sistema de Propostas Mel Simão

Contrato operacional deste repo. A especificação completa (requisitos, árvore do formulário, critérios de aceite) está em `PRD.md`, que é a fonte de verdade do produto. Este arquivo define como trabalhar aqui. Em conflito entre os dois, o PRD define O QUE, este arquivo define COMO.

## Contexto em 2 linhas

MVP: lead preenche formulário multi-etapas estilo Typeform em `/formulario`, sistema gera PDF fiel à arte do Figma, Mel aprova no painel `/admin` e envia por e-mail + WhatsApp. O anúncio de casamento chega antes pela LP de venda `/casamento`. Prazo de 2 dias, custo de infra R$ 0 (free tiers). Produção: `https://melstorymaker.com.br` (DNS gerenciado no Registro.br).

## Stack (travada, não sugerir alternativas)

- Next.js 14+ App Router, TypeScript strict
- Tailwind + shadcn/ui + Framer Motion (só nas transições do form)
- Supabase: Postgres, Auth, Storage
- pdf-lib + @pdf-lib/fontkit
- Nodemailer + Gmail SMTP, atrás de `MailAdapter`
- Deploy: Vercel

## Comandos

```bash
npm run dev          # ambiente local
npm run build        # build de produção (rodar antes de todo commit relevante)
npm run lint         # ESLint
npx tsc --noEmit     # checagem de tipos
npm run lp:reels     # mídia da LP /casamento (Reels brutos > vídeo, preview, pôster); só refaz o que mudou
npm run lp:og        # imagem de compartilhamento da LP
```

Schema do banco: aplicar `supabase/schema.sql` manualmente no SQL Editor do Supabase. Não usar migrations automáticas neste MVP.

## Decisões travadas (NUNCA reabrir nem "melhorar")

1. PDF gerado com pdf-lib sobre os PDFs base do Figma. Nunca Puppeteer, Chromium, headless browser ou API do Figma em runtime.
2. E-mail sempre pela interface `MailAdapter`, com `GmailAdapter` (SMTP do Gmail da Mel, App Password) como único provider. Nunca chamar Nodemailer direto de uma rota: é a interface que garante que a trava do `MAIL_DRY_RUN` não seja contornada. **Sem serviço transacional de e-mail** — a conta Workspace entrega 2.000 destinatários/dia e o volume da Mel é muito menor. Não introduzir um sem que o volume mude de ordem de grandeza.
2b. O remetente é `mel@wama.digital`, e isso é **deliberado** — não é migração pendente para `@melstorymaker.com.br`. Decisão do owner em 18/08/2026: o nome de exibição ("Mel Simão | Storymaker") é o que o lead lê, e o endereço da agência não atrapalha. Não trocar sem pedido explícito: mudar exigiria criar o endereço no Workspace e alteraria `GMAIL_USER` junto, já que o Google reescreve o remetente.
3. WhatsApp = links `wa.me` gerados no painel. Nenhuma API de WhatsApp (Twilio, Z-API, Evolution, Baileys) **para falar com o lead ou enviar do número da Mel** — a trava protege o número dela de banimento. Exceção aprovada pelo owner (18/08/2026): notificação interna de lead novo via CallMeBot (`lib/notifica/`), em que a Mel só RECEBE de um gateway; conteúdo mínimo (sem e-mail nem telefone do lead na mensagem), falha nunca quebra o submit (`after()` + try/catch), e sem `NOTIFICA_WHATSAPP_APIKEY` é no-op. Essa exceção também retira a notificação de lead novo do escopo v2 proibido da regra 8. **A única env obrigatória é a apikey**: o número vem de `MEL_WHATSAPP`, e `NOTIFICA_WHATSAPP_FONE` só existe para mandar o aviso a um aparelho diferente. Pedir o mesmo telefone em duas variáveis já deixou a notificação muda em produção (20/08/2026, apikey configurada e fone não). A notificação dispara **no submit** (`incompleto` → `aguardando_revisao`), não na criação do lead: avisar na criação significaria uma mensagem para cada pessoa que escolheu a categoria e desistiu.
4. Human-in-the-loop: nenhum e-mail sai para o lead sem ação explícita da Mel no painel. Não criar envio automático pós-submit.
5. Formulário renderizado 100% a partir de `lib/form/arvore.json`. Perguntas nunca hardcoded em componentes. Nova pergunta = mudança no JSON.
5b. **A tela de abertura tem DUAS portas**, decisão do owner em 03/09/2026: "Falar com a Mel" (esquerda, link `wa.me` com a primeira mensagem já escrita) e "Quero um orçamento" (direita, o formulário de sempre). O problema era gente que não preenchia o formulário E não chamava no WhatsApp — sem porta de saída rápida, quem não queria responder oito perguntas simplesmente fechava a aba. As duas caixas têm a mesma forma e a mesma altura mínima (`PORTA`, em `FormularioClient.tsx`): são alternativas de peso igual, e uma mais baixa leria como opção secundária. A mensagem pré-escrita (`mensagemPrimeiroContato`, `lib/whatsapp.ts`) não é enfeite — caixa de texto vazia para um número desconhecido é exatamente onde a pessoa desiste. Sem `MEL_WHATSAPP` a porta da esquerda some e a da direita ocupa a linha inteira: link `wa.me` sem número abre o seletor de conversas do próprio lead, que não leva a lugar nenhum.
5e. **`/orcamento` é o link que a Mel manda**, pedido do owner em 30/09/2026: o mesmo formulário, abrindo direto na escolha do evento, sem as duas portas. Quem recebe o link já está conversando com ela — a porta "Falar com a Mel" seria mandar a pessoa de volta para a conversa de onde veio. As portas continuam em `/formulario` (e na raiz `/`), que é para onde apontam a bio e os anúncios que não são de casamento (o de casamento aponta para a LP `/casamento`, ver 5f). A tela inicial desce do servidor como prop (`inicio`), nunca lida da URL no navegador: o conteúdo precisa estar no HTML inicial (LCP) e o hidratado tem que bater com ele. Página própria e não redirect: seria uma ida e volta a mais no 4G antes da primeira pintura.
5f. **`/formulario?evento=<categoria>` é o "modo casamento"**, pedido do owner em 01/10/2026 para a LP `/casamento`. O `?evento` é lido NO SERVIDOR (`app/formulario/page.tsx`, mesma regra da 5e) e só vale se for categoria válida. Muda quatro coisas e nada mais: o subtítulo da abertura (`boas_vindas.por_categoria` no `arvore.json`, nunca no componente), a mensagem pronta da porta "Falar com a Mel" (`mensagemPrimeiroContato(categoria)`; só casamento tem texto próprio, aprovado pelo owner, e qualquer outra categoria cai no genérico) o `content_category` do `Contact` dessa porta, e a porta "Quero um orçamento", que pula a escolha de categoria e vai direto à pergunta do WhatsApp. O voltar da primeira pergunta leva de novo às portas só quando a pessoa entrou por ali (`pulouCategoria`); **lead retomado nunca liga essa marca**, porque das portas a porta direita trocaria a categoria dele em silêncio, e a troca apaga as respostas do fluxo e grava no banco. `/orcamento` ignora `?evento` de propósito: é o link de quem já está conversando com a Mel. Sem `?evento`, o formulário é idêntico ao de antes.
5g. **Horário e local aceitam "decidir depois"** (pedido do owner em 03/10/2026: os leads paravam no horário do casamento). Todo `horario` e todo `local*` do `arvore.json` tem `a_definir`, o rótulo da caixa: "Decidir isso depois" no horário, "Ainda não decidi" nos locais (inclusive o do making of). Marcada, a resposta grava `A_DEFINIR` ("A definir", `lib/form/types.ts`) e vale como respondida na validação e no submit; vazio continua recusado, com a mensagem apontando a caixa. **Nunca em resposta que vai para a arte do PDF ou para coluna do banco**, e só em `texto` e `hora`: "A definir" sairia impresso na capa, e em `data` a coluna é `date`. O `engine.test.ts` guarda as duas pontas (todo horário e local com a caixa; nenhuma caixa fora do lugar). No contrato, `dadosIniciais` lê "A definir" como vazio: horário e local seguem faltando e a Mel confirma com o cliente (passado adiante, o marcador viraria endereço válido). A marca é estado próprio do campo, nascido da resposta, e não `valor === A_DEFINIR` a cada render: senão o campo travaria na última letra de quem digitasse "A definir" à mão. No painel a mesma caixa aparece, com o rótulo "A definir": campo de hora não mostra texto, e sem ela a Mel veria o horário em branco e acharia que o lead pulou a pergunta.
5d. **O lead nasce no PRIMEIRO AVANÇO, não na escolha da categoria** (decisão do owner em 03/09/2026). Escolher categoria só muda de tela; o `POST /api/leads` sai quando a pessoa responde o WhatsApp e aperta OK, e leva as respostas junto — nunca um POST vazio seguido de PATCH, que recriaria por um instante exatamente o registro que este desenho evita. Motivo: lead sem telefone não é lead, é linha inalcançável enchendo a coluna "Novo". Este é o único avanço que ESPERA a rede (sem id não há o que salvar depois); os outros seguem otimistas. A rota mantém `respostas` opcional de propósito — é contrato de API e quem chama sem elas continua funcionando.
5c. **O WhatsApp é a PRIMEIRA pergunta de todo fluxo**, e o e-mail a última. É a única resposta que continua servindo quando o lead abandona no meio; perguntado no fim (como era até 03/09/2026), todo abandono virava um registro que a Mel não tinha como contatar. Por isso `arvore.contato` é um par de listas (`abertura` e `fechamento`) e não uma lista só: quem manda na ordem continua sendo o JSON, e `sequencia()` no engine só concatena — nenhum id de pergunta aparece hardcoded lá. Mexer nisso quebra os testes de ordem em `engine.test.ts`, que existem para isso.
6. Sem lógica de preço. Valores estão desenhados na arte estática dos templates. **Formato: `R$ XXX`** — o cifrão é um nó de texto SEPARADO do número no Figma (DM Sans Bold 18,11, mesma cor do número, borda direita ~10px à esquerda dele). Por ser separado, ele some sem alarde: em 20/08/2026 nove preços estavam sem cifrão em `aniversario_infantil_03`, `corporativo_03` e `corporativo_04`. Ao mexer em preço, auditar que todo número de 3–5 dígitos tem um `R$` pareado na mesma linha.
6b. Categoria (4, enum do Postgres) e arte (5, `TemplateId`) são conceitos separados. `aniversario` resolve entre `aniversario_infantil` (14 anos ou menos) e `aniversario_adulto` (15+) via `resolverTemplateId(categoria, respostas)`. Nunca indexar template por categoria, e nunca acrescentar valor ao enum para criar arte nova — isso geraria migration à toa.
6c. **Existe mais de uma TABELA de preço, e cada uma é um jogo próprio de PDFs base**: `assets/templates/<arte>.<tabela>.pdf`. Como o preço é pixel dentro do JPEG da arte (4d/4e), reajuste nunca é mexer em variável — é publicar outra arte. A tabela sai do **ANO DO EVENTO** (`respostas.data`), nunca da data em que o lead preencheu: quem marca festa para 2027 contrata pela tabela de 2027 mesmo tendo preenchido em 2026. Vigências em `lib/pdf/precos.ts`; vale a última tabela cujo ano já chegou, então um evento de 2029 segue na de 2027 até alguém criar outra. O ano é lido da STRING ISO, nunca via `new Date` — `new Date("2027-01-01")` é meia-noite em UTC e `getFullYear()` em São Paulo devolveria 2026, jogando o primeiro dia da tabela nova na tabela velha.
6d. Tabela **2027 aprovada pelo owner em 28/08/2026**: +15% sobre 2026, arredondado para cima até número comercial. **Só os PACOTES mudaram** — opcionais, locomoção, reserva de 30% e validade de 3 meses são idênticos às de 2026. Isso vale para a 2027 e **não** para a 2028 (ver 6f): não generalizar "reajuste mexe só em pacote". Os valores aprovados vivem em `PACOTES` (`precos.ts`) como ESPECIFICAÇÃO, não como fonte da geração: quem manda é o pixel da arte. O `arte:preparar` imprime a lista na hora do preparo, para conferir contra as páginas exportadas, e `precos.test.ts` prova que o reajuste respeita os 15%.
6f. **Tabela 2028 aprovada pelo owner em 30/09/2026: +20% sobre a de 2027 — e desta vez os OPCIONAIS subiram junto**, ao contrário do que a 6d registra para 2027. Duas grades diferentes, de propósito: pacote arredonda para cima até o próximo número terminado em **50 ou 90** (a mesma da 2027 — ela reproduz os catorze valores daquela tabela exatamente, e `precos.test.ts` prova as duas travessias); opcional arredonda para cima até o próximo múltiplo de **50**, porque a grade 50/90 aplicada a valor de 2–3 dígitos distorce demais. Mesmo assim o reajuste efetivo dos opcionais vai de +20% a +50% (o pior é o storymaker/hora do infantil, R$ 100 → R$ 150, e ele é **por hora**, então numa cobertura de 5h o cliente sente R$ 500 → R$ 750). Nos pacotes o efetivo fica entre +20,1% e +22,9%.
6g. **Preço de opcional é POR TABELA (`ValorPorTabela` em `lib/contrato/catalogo.ts`) e NUNCA se reajusta no lugar.** O catálogo pré-preenche contrato de qualquer ano, inclusive um de 2026 que a Mel reabra hoje: trocar o número onde ele está faria o reajuste retroagir sobre proposta já aceita (CDC art. 40 §2º, o mesmo motivo que mantém `PACOTES` por tabela). O helper `porTabela({...})` preenche **para a frente** — tabela nova que não mexe nos opcionais não exige editar o catálogo, e quando mexe só as linhas alteradas aparecem no diff. `valorCatalogoAdicional` e `novoAdicional` exigem a tabela sem valor padrão: um padrão silencioso serviria o preço de um ano para o contrato de outro. Dois testes guardam isso em `catalogo.test.ts`: um prova que 2026 e 2027 continuam idênticas, o outro que 2028 é a grade aplicada à 2027.
6h. **O bullet "Entrega em tempo real: Adicional de R$ N" do aniversário adulto sai do próprio adicional**, via `itensArteDaTabela` e o marcador `{tempo_real}` — nunca escrito à mão em `itensArte`. O número aparecia duas vezes (em `valorPorPacote` e dentro do texto) e as duas cópias divergiriam no primeiro reajuste que alguém esquecesse de espelhar. `itensArte` **nunca chega ao PDF do contrato**: é lido pelo painel e, desde 01/10/2026, pela LP `/casamento` (sem o bullet de prazo, ver "LP de venda"), então o `contrato:verificar` não o alcança — quem prova que nenhum marcador vaza é `catalogo.test.ts`. O `PROIBIDOS` do `contrato:verificar` ganhou `{` e `}` sozinhos pela mesma razão.
6i. **Tabela nova pode nascer no código ANTES da arte, e aí fica FORA de `VIGENCIAS` até as cinco artes existirem.** Foi assim que a 2028 entrou: valores e testes em 30/09/2026, arte e vigência em 01/10/2026. Ligar a vigência sem arte não dá preço velho: dá 409 em toda geração do ano (6e), e a Mel fica sem atender o ano inteiro. Nesse intervalo o `pdf:verificar` fica vermelho dizendo "tabela N ainda não tem vigência" e listando as combinações arte × tabela sem cenário — vermelho esperado, e é ele que lembra de ligar as duas coisas juntas. `precos.test.ts` fecha a porta do outro lado, e esse é o invariante permanente: **toda tabela em `VIGENCIAS` tem os cinco `<arte>.<tabela>.pdf` no repositório**. O caminho inverso (arte publicada, vigência ainda desligada) continua verde de propósito. O seletor de tabela do contrato mostra tabela sem arte e avisa que a proposta ainda sai pelo ano do evento — a Mel pode legitimamente fechar hoje um evento do ano novo pelo preço novo.
6e. **Arte de uma tabela faltando ABORTA a geração** (`ArteFaltandoError` → 409 com texto humano no painel, caminho do arquivo só no log). Nunca cair na arte de outro ano: seria enviar proposta com preço defasado sem ninguém perceber — mesma lógica do campo vazio (5b). Pelo mesmo motivo o placeholder só vale para a tabela base: placeholder não tem preço desenhado, então não representa tabela nenhuma.
7. Sem banners de cookies, telas de consentimento ou fluxos de LGPD. Decisão de escopo do owner.
8. Escopo v2 do PRD (seção 19) é proibido no MVP: sem tracking de abertura, sem agenda, sem pagamento, sem analytics de funil, sem notificações em tempo real. Exceções: o Meta Pixel (8b), que existe para as campanhas de anúncio, não para painel de funil (os eventos personalizados da LP e do formulário também: o funil é lido NA META, no Gerenciador de Eventos e de Anúncios, a pedido do owner em 05/10/2026; nenhum painel nosso lê ou mostra esses dados); e o contrato com o cliente (8c).
8c. **Contrato de prestação de serviço** (`lib/contrato/`, seção "Contrato" no detalhe do lead), pedido do owner em 29/09/2026. Tira "contrato" do escopo v2 proibido; **pagamento continua fora** — o contrato diz como pagar, o sistema não cobra nem confere PIX. Só o contrato em que a Mel é a CONTRATADA: subcontratar outra storymaker tem estrutura própria (multa por atraso, vestimenta, uso exclusivo das imagens) e ficou fora. É também a primeira parte PAGA do sistema, fora do "custo de infra R$ 0": a API da Anthropic (o owner pediu o modelo mais capaz — o contrato sai poucas vezes por mês, e economizar ali não é prioridade) e os créditos de assinatura da iLoveAPI. Regras em "Contrato: gotchas obrigatórios".
8b. **Meta Pixel + Conversions API** (`lib/meta/`), pedido do owner em 29/09/2026. Pixel `28251176377887999`, lido de `META_PIXEL_ID` no servidor (prop, não `NEXT_PUBLIC`), configurado na Vercel só em production — preview e dev não sujam o Pixel. No formulário a página é dinâmica e lê a cada request; na LP `/casamento`, que é estática, lê no build (na Vercel, trocar env já exige redeploy de todo jeito). Mapa de eventos, em `lib/meta/eventos.ts`:
   - **Navegador, só nas páginas do lead (`/formulario`, `/orcamento` e a LP `/casamento`)**: `PageView`; `Contact` na porta "Falar com a Mel" e no WhatsApp e no e-mail do rodapé da LP, com `content_category` quando a categoria é conhecida e `canal` (`whatsapp`/`email`); `IniciouOrcamento` (personalizado, `EVENTO_FORMULARIO`) quando a pessoa entra no fluxo do orçamento, o degrau entre a visita e o `Lead`; `Lead` quando o lead NASCE (primeiro avanço, com o WhatsApp — mesma definição da 5d, não o fim do formulário); `SubmitApplication` no submit.
   - **Na LP** (pedido do owner em 05/10/2026: ler TODO o caminho de quem chega pelo anúncio): `ViewContent` (`content_category: casamento`) disparado NO MESMO snippet do PageView (`eventosIniciais` do `PixelMeta`), nunca num `useEffect`, que pode rodar antes do `fbq` existir; e os PERSONALIZADOS de `EVENTO_LP`: `CliqueCTA` `{pagina, posicao}`, `AssistiuReel` `{reel, marco: abriu|metade|fim}`, `RolouPagina` `{profundidade: 25|50|75|90}`, `ViuSecao` `{secao}` (o `data-secao` de cada seção da página), `TempoNaPagina` `{segundos: 15|30|60|120}`, com a aba visível, `AbriuDuvida` `{pergunta}` (o `data-duvida` do FAQ, slug do título) e `CliqueLink` `{destino: instagram}`. Cada marco sai uma vez por visita. Rolagem, seções, tempo, FAQ e links moram em `RastreioLp` (`components/lp/`), por delegação e por atributo, para a página continuar server component; as regras de quando contar são puras, em `lib/meta/engajamento.ts`, com teste. Seção nova na página = `data-secao` nela. O CTA leva `evento=casamento&cta=<posição>` na URL, e essa continua sendo a prova do clique que sempre chega (o PageView do formulário).
   - **Servidor (Conversions API)**: cópia de `Lead` e `SubmitApplication` com o MESMO `event_id` (`idEvento`) — a Meta deduplica e quem tem bloqueador continua contado. **Todo o resto do navegador também tem cópia** (05/10/2026), pela rota pública `POST /api/meta/eventos`: `rastrearComCopia` dispara no Pixel com um `eventID` aleatório e põe o evento numa fila, que sai em lote por `sendBeacon` (a cada ~2 s, ou na hora quando o clique sai da página, ou ao esconder a aba). O PageView e o ViewContent do snippet saem com id gerado no próprio snippet e ficam em `window.__metaIniciais` até o `CopiaIniciais` mandá-los. O lote que não é urgente espera até 5 s pelo fbevents.js (`fbq.callMethod`): é ele que grava o `_fbp`, que liga o evento do servidor ao navegador, e que reescreve o `_fbc` de quem volta por um anúncio novo. No servidor, o `fbclid` da URL vence um `_fbc` de OUTRO clique (`rastreioDaRequisicao`), como o próprio fbevents.js faz; com o mesmo clique, o cookie fica. A rota é a superfície de abuso: só aceita os eventos de `COPIAVEIS` e só os parâmetros de cada um, valores curtos, URL (do corpo ou do Referer) do próprio host, recusa `Sec-Fetch-Site` de outro site, 60 lotes/min por IP, e **nunca** `Lead` nem `SubmitApplication` (seria fabricar lead no Pixel com um POST); a validação é pura, em `lib/meta/copias.ts`, com teste, e um teste quebra se um evento de `EVENTO_LP`/`EVENTO_FORMULARIO` ficar fora de `COPIAVEIS`. Para o site responde sempre 204 e envia no `after()`. E os eventos do **quadro**, que só podem sair do servidor porque o lead não está na página: `PropostaEnviada` (entrar em `enviado`, pelo e-mail ou pelo arraste), `VirouCliente`, `LeadPerdido`. Voltar para revisão não é evento.
   - **Personalizados e não `Purchase`**: `Purchase` exige valor, e este sistema não sabe quanto o cliente fechou (regra 6). Valor inventado estragaria o ROAS. Quem quiser coluna no Gerenciador cria conversão personalizada em cima deles.
   - **Nunca no layout raiz nem no `/admin`**: cada visita da Mel ao painel viraria PageView e ela entraria no próprio público de remarketing.

## Dados e segurança

- O client NUNCA fala direto com o Supabase para leads. Todo acesso via route handlers usando `SUPABASE_SERVICE_ROLE_KEY` (server-side only).
- RLS ativado na tabela `leads` com zero policies públicas. Se um acesso falhar por RLS, a correção é no route handler, nunca criar policy pública.
- `respostas` é jsonb: mudança na árvore de perguntas não gera migration.
- **Leitura do painel passa por `lerComRetentativa`** (`lib/supabase/consulta.ts`). Em 22/08/2026 o quadro mostrou "JWT issued at future" em UMA das quatro colunas enquanto as outras três carregavam no mesmo request. A causa é do lado do Supabase — a chave `sb_secret_` é trocada por um JWT curto dentro da infra deles, e quando o nó que assina está um instante à frente do que valida, o `iat` cai no futuro. Não é o relógio da máquina (medido: 0s de desvio) nem a nossa chave (não é JWT). Repetir resolve, porque a próxima requisição pega outro nó. **Só para leitura** — em insert/update/delete retentativa pode duplicar escrita.
- **Erro de upstream nunca vai cru para a tela.** A Mel não tem o que fazer com "JWT issued at future"; a mensagem técnica vai para o log do servidor e a tela mostra texto humano + "Tentar de novo". O erro da coluna não era logado, e por isso não havia rastro nenhum nos logs da Vercel.
- Colunas promovidas (`nome_display`, `data_evento`, `email`, `whatsapp`) são atualizadas no autosave, junto com o jsonb.
- `rastreio` (jsonb, `{fbp, fbc, ua, ip}`) é escrito uma vez, na criação, e só serve à Conversions API (8b). Não é resposta do lead: nunca misturar em `respostas`, onde o whitelist do `arvore.json` o descartaria no primeiro autosave.
- Transições de status apenas nos endpoints definidos: `incompleto` (criação) > `aguardando_revisao` (submit) > `enviado` (envio de e-mail) e, desde 20/08/2026, **`PATCH /api/admin/leads/[id]/status`**, a única em que uma pessoa (a Mel, arrastando no quadro) escreve status. A matriz de transição vive em `lib/admin/status.ts` e vale nos dois lados: o servidor recusa com 422, o cliente desabilita o item de menu.
- **`incompleto` NUNCA é destino.** Não é só uma raia do funil: é a única que devolve permissão de ESCRITA a quem tiver o UUID — reabre o autosave público sobre respostas já revisadas e re-arma o `submit`, que dispara `notificarMel()` de novo (a Mel recebe "lead novo" por um lead que ela mesma moveu). O `scripts/e2e-quadro.ts` prova isso: depois do 422, confere que o `PATCH /api/leads/[id]` público segue 409.
- **Coluna proibida no quadro nunca usa `disabled` no `useDroppable`.** Com `disabled`, o `closestCorners` elege o droppable mais próximo e o cartão mirado em "Novo" era solto em "Aguardando revisão", em silêncio. A coluna recebe o drop e `mover()` recusa com toast explicando. Coberto por `npm run e2e:arraste`.
- **Lead de "Novo" com telefone ganha "Chamar no WhatsApp"** (cartão do quadro e detalhe do lead), pedido do owner em 22/09/2026. Só em `incompleto`: de `aguardando_revisao` em diante a ação certa é gerar a proposta, não puxar conversa. No detalhe o botão some quando já existe PDF — ali o botão certo é "Enviar via WhatsApp", e dois botões de WhatsApp lado a lado obrigariam a Mel a escolher entre eles a cada lead. `linkConversaLead` devolve `null` sem número e o botão simplesmente não aparece: um `wa.me` sem destinatário abriria o seletor de conversas da própria Mel, que não é chamar ninguém. **A conversa abre VAZIA, sem texto pré-escrito** (decisão do owner em 22/09/2026) — é a única porta de WhatsApp do projeto assim. As outras levam mensagem pronta porque são repetíveis: a mesma proposta, a mesma cobrança de 7 dias. Esta não é: cada pessoa parou num ponto diferente por um motivo diferente, e quem sabe o que dizer é a Mel. Nada é carimbado também: é link puro, sem registro de "já chamei".
- **Lead de "Novo" com e-mail ganha "Lembrar por e-mail"** (cartão do quadro, embaixo do "Chamar no WhatsApp"), pedido do owner em 05/10/2026. **O clique ENVIA**, na hora e sem confirmação — e nada sai sem ele (regra 4) —, pela `POST /api/admin/leads/[id]/lembrete-email`; depois o botão vira "Lembrete enviado" e trava por **7 dias** contados de `lembrete_email_em`, com "Libera de novo em N dias" escrito embaixo (botão desabilitado não mostra `title`). A rota **carimba antes de enviar**, numa escrita condicional sobre o `lembrete_email_em` que acabou de ler, e devolve o valor anterior se o SMTP falhar: dois cliques ou duas abas nunca mandam dois e-mails (o `e2e:quadro` dispara os dois ao mesmo tempo e exige um 200 e um 409). Não mexe em status: o lead segue em "Novo" até terminar o formulário. **O link do e-mail é `/continuar/{id}`, nunca `/formulario`.** A retomada é pelo localStorage do aparelho em que o lead começou, e quem abre o e-mail está quase sempre em outro navegador (o formulário foi preenchido no do Instagram ou do WhatsApp; o link abre no do Gmail). A página de passagem grava `CHAVE_LEAD` (`lib/form/retomada.ts`, a mesma do `FormularioClient`, conferida por teste) e segue para `/formulario`, que retoma sozinho. Página própria e não `?lead=` porque o id do lead é a chave de escrita do autosave público enquanto ele está em "Novo": ali não há Pixel, e o `no-referrer` faz o `/formulario` abrir com `document.referrer` vazio — o PageView sai com `dl` limpo e `rl` vazio, e o id nunca chega à Meta. Copy provisória em `montarEmailLembrete` (`lib/mail/templates.ts`), sem pixel de abertura (regra 8). **Quase nenhum lead de "Novo" tem e-mail**: o e-mail é a última pergunta (5c) e responder ela já envia o formulário, então o botão aparece quando o envio final falha depois de o e-mail ser salvo, ou quando a Mel completa o e-mail no detalhe do lead. Em 05/10/2026, 0 dos 9 leads em "Novo" tinham e-mail.
- **Cobrança de quem sumiu depois de receber a proposta** (`lib/admin/lembretes.ts`), pedida pelo owner em 03/09/2026. O relógio conta a partir de `enviado_em` e SÓ dentro da coluna `enviado`. Aos **7 dias** o cartão fica âmbar com o botão "Relembrar cliente"; aos **30**, vermelho com "Última tentativa". Clicar abre o `wa.me` do lead com a mensagem pronta **e** carimba `lembrete_7_em`/`lembrete_30_em` no mesmo clique — separar daria um segundo passo que ninguém faz, e o cartão ficaria vermelho para sempre. O carimbo é AFIRMAÇÃO da Mel, não prova de entrega (regra 3: não existe API de WhatsApp aqui para confirmar), e por isso o toast traz "Desfazer". Cobrado, o cartão silencia e mostra o selo "Lembrado aos N dias" — é esse selo que diz à Mel que dá para arquivar. Nada disso é automático (regra 4): quem move para "Lead perdido" é ela.
- **Cobrança vencida sobe na coluna** (`compararPorCobranca`), com o vermelho na frente do âmbar e, dentro da mesma faixa, quem espera há mais tempo. A ordenação é no CLIENTE porque "vencido" não existe no banco: sai de `enviado_em` cruzado com o agora e com as duas datas de lembrete. Fora de "Enviado" o comparador devolve 0 para todo mundo, e como `sort` é estável a ordem do servidor sobrevive — ordenar as outras raias por tempo de espera inverteria o "mais novo primeiro" sem ninguém pedir.
- **A consulta de "Enviado" ordena por `enviado_em` ASC**, ao contrário das outras quatro (`created_at` DESC). Não é inconsistência: "Enviado" é a raia que acumula, e cobrança vencida só existe em quem foi enviado há mais tempo. Com `created_at`, o dia em que a coluna passasse de `LIMITE_COLUNA` seria o dia em que os vencidos parariam de ser buscados — e o quadro deixaria de mostrar em silêncio exatamente os cartões que pedem ação. Assim o corte cai sobre os envios recentes, que não precisam de nada.
- **A contagem usa `enviado_em`, que nunca é reiniciado.** Cartão que voltou para revisão e depois voltou para "Enviado" continua contando do envio original — o lead não esquece que recebeu a proposta há 40 dias porque a Mel reorganizou o quadro.
- **`agoraMs` desce do SERVIDOR como prop** até o `CartaoLead`. Nunca `Date.now()` dentro do componente: o painel é renderizado no servidor e hidratado no navegador, e dois relógios na mesma árvore dariam hydration mismatch exatamente na fronteira do 7º dia.
- **`perdido` é a 5ª raia, e é cinza (stone), não vermelha.** O vermelho já é do cartão que PRECISA de cobrança dentro de "Enviado"; pintar as duas coisas de vermelho faria o quadro gritar justamente onde ele deveria silenciar. No celular ela nasce FECHADA no accordion — é a única raia que não pede ação, e aberta empurraria as quatro que pedem para fora da primeira tela.
- **Status novo no enum obriga a mexer em `grid-cols` na mão**, em `QuadroLeads` (`lg:grid-cols-5`) e `FaixaDestinos` (`grid-cols-5`). As classes são literais porque o scanner do Tailwind não lê string interpolada — derivar de `STATUS.length` faria a classe sumir do CSS.
- Marcar como "Enviado" pelo quadro **não manda e-mail** (regra 4 continua de pé): pede confirmação quando `enviado_em` é nulo e carimba a data, porque o caso real é a Mel ter mandado pelo WhatsApp. Sair de "Enviado" **nunca** limpa `enviado_em` — e-mail não desenvia.
- **O detalhe do lead tem atalhos de coluna** (`AtalhosStatus`, pedido do owner em 03/10/2026): "Marcar como enviado" (azul), "Marcar como cliente" (verde) e "Marcar como perdido" (cinza), com a mesma tinta da coluna de destino (`CLASSE_ATALHO`, literal). Mover sem arrastar, de dentro do lead. É o MESMO `PATCH .../status` do arraste, com o `de` que a tela mostra, e as regras são as mesmas funções do quadro (`estadoDoAtalho` sobre `recusarMovimento`; `pedeConfirmacaoDeEnvio`), então o atalho nunca deixa o que o arraste recusaria e os eventos da Meta saem iguais. Só esses três destinos: "Novo" é travado e "Aguardando revisão" é consequência do submit. O motivo de um atalho bloqueado ("Gere a proposta antes...") vai escrito embaixo, não em `title`: botão desabilitado do shadcn tem `pointer-events: none` e não mostra tooltip.
- Nunca commitar `.env`, App Password ou service role key. Nunca expor a service role no bundle do client.

## PDF: gotchas obrigatórios

1. pdf-lib usa origem no canto INFERIOR esquerdo da página. Converter coordenadas vindas do Figma (origem superior esquerda): `y_pdf = alturaPagina - y_figma - tamanhoFonte`.
2. Chamar `pdfDoc.registerFontkit(fontkit)` ANTES de embutir qualquer fonte custom.
3. Campo com `maxLargura`: reduzir o tamanho da fonte proporcionalmente até caber. Nunca quebrar linha em campo de nome.
4. Criar a rota de calibração `/admin/debug-template?template=X` (grid de coordenadas a cada 20pt sobre o PDF base) ANTES de calibrar o primeiro template. Calibrar sem ela é proibido. O parâmetro é o `TemplateId`, não a categoria: `aniversario` sozinho é ambíguo. Aceita também `&tabela=` (padrão: a base) — cada tabela tem PDF base próprio, e o grid sobre a arte de 2026 não prova nada sobre a de 2027.
4b. **Preparo da arte** (mudança de arte = PR dedicada): esvaziar os placeholders no Figma (manter só `Olá,` no bloco de saudação, ocultar o cabeçalho), exportar cada frame com `download_assets` em PDF e rodar `npm run arte:preparar -- <template> <tabela> <pasta>`. A **tabela é posicional e obrigatória**, não flag com padrão: errá-la sobrescreve em silêncio a arte de um ano com as páginas de outro. O Ghostscript roda SÓ nesse preparo, rasterizando cada página; em produção continua apenas pdf-lib. **Depois de mudar a arte, os PDFs já gerados continuam com a arte velha** — só saem atualizados quando a Mel clicar em Gerar PDF de novo (o link não muda, RF-14).
4c. As cinco capas compartilham o mesmo desenho, montado por `camposCapa()` em `templates.config.ts`. Arte nova = uma chamada, variando a composição do cabeçalho e o `x` do nome.
4d. **A arte base é RASTERIZADA: um JPEG por página, sobre página A4 (595x842 pt).** O export do Figma é vetorial e trazia ~96 mil operações de path (o padrão topográfico) + 51 grupos de transparência; o visualizador de PDF do celular estourava o orçamento de renderização e pintava a página **branca**, só mostrando o conteúdo depois de um zoom que o obrigava a redesenhar em blocos. Reduzir a página para A4 sozinho **não resolveu** — foi preciso rasterizar. Resultado: de 96.405 operações de path para 10, e 12,05 → 3,25 MB no conjunto das 5 artes.
4e. O texto que o lead lê como DADO (nome, data, cabeçalho) **não** está no raster: é desenhado pelo pdf-lib em runtime, continua vetorial e nítido em qualquer zoom. O que virou pixel é o texto *da arte* — títulos, corpo, preços. Trade-off aceito pelo owner em 19/08/2026, tendo como alternativa o PDF branco no celular.
4f. `escala: ESCALA_ARTE` (595/1240) em todas as artes, nunca `1`: as coordenadas do config continuam sendo as do painel do Figma e a escala multiplica x, y e tamanho de fonte no `gerar.ts`. Verificação: gere e meça: o cabeçalho do casamento deve terminar em x≈552 pt.
4g. A peça é **100% digital** — ninguém imprime. O alvo é a tela: `--altura 2000` px por página (~171 DPI em A4). Subiu de 1280 (~109 DPI) em 20/08/2026 porque naquela resolução o texto *da arte* ficava visivelmente mole ao dar zoom. Como a arte inteira é imagem, essa altura é o único controle de nitidez que resta. `arte:preparar -- <arte> <pasta> [--altura PX] [--qualidade N]`.
4h. **O caminho vetorial já foi tentado e não resolve — não repetir.** Converter só as ondas em PNG (feito no Figma e que continua valendo) zerou os grupos de transparência (51 → 0), mas os paths caíram apenas de 96.405 para 78.027, e no celular a página continuou branca. A razão: **o Figma exporta texto como CONTORNO, sem fonte embutida** (zero `/FontFile` no PDF). Cada letra vira dezenas de curvas e só o corpo de texto responde por ~12 mil operações por página — nada que o Ghostscript alcance.
4i. As ondas do padrão topográfico **já estão como PNG dentro do Figma**, convertidas em 19/08/2026 com o vetor original oculto ao lado (`ondas (vetor original, oculto)`). Não desfazer: era o que sustentava os 51 grupos de transparência. Ao mexer na arte, o critério de "onda" é ≥3000 segmentos de path **e zero nós de texto** — sem a segunda condição o bloco de contato da Mel (telefone, e-mail, CNPJ) é confundido com decoração.
4j. **Tabela de preço nova NÃO se prepara do zero: deriva-se da anterior.** `npm run arte:derivar -- <arte> <tabelaOrigem> <tabelaDestino> <pasta>` copia a arte já publicada página por página e troca só as que estão na pasta, nomeadas pelo NÚMERO da página (`03.pdf` troca a terceira). Entre duas tabelas muda o preço e mais nada — remontar tudo a partir de um reexport abriria espaço para as páginas comuns divergirem por algo que ninguém pediu (uma foto trocada no Figma desde o último preparo). Derivando, a única diferença possível é a pretendida, e dá para **provar**: rasterize as duas artes e compare página a página; só a de Pacotes pode diferir. Foi assim que a tabela 2027 entrou, em 28/08/2026.
4k. Os parâmetros de raster (altura 2000, qualidade 82, A4) moram em `scripts/arte-raster.ts`, **compartilhados** por `arte:preparar` e `arte:derivar`. Nunca duplicar: se divergirem, a página trocada sai com nitidez diferente das vizinhas dentro do mesmo PDF, e como a arte inteira é imagem isso aparece na tela do lead.
4l. No Figma, cada tabela tem seu próprio frame de Pacotes, nomeado `<arte>_NN_tabela<ano>` (ex.: `casamento_04_tabela2027`), logo abaixo do original na mesma coluna. **Não editar o preço no frame de 2026 para gerar o de 2027** — os dois precisam continuar existindo, senão a arte da tabela antiga deixa de ser reproduzível. Os preços têm largura automática e o dígito do DM Sans não é tabular (o `0` mede ~30px, o `1` ~14px): ao trocar o número, ancore pela **borda direita** (`x = direitaAntiga - larguraNova`) e desloque o nó `R$` mantendo o mesmo respiro — fora do casamento, onde o `R$` faz parte do mesmo nó de texto.
5. Formatação sempre via `lib/pdf/formatadores.ts`: **data em DD/MM/AAAA** ("14/03/2026") em TODOS os PDFs, hora no padrão "19h30". O formatador `data_extenso` continua disponível no registry, mas nenhuma arte usa.
5b. **Campo do config vazio aborta a geração.** Todo campo de `templates.config.ts` é obrigatório salvo `opcional: true`. Faltando qualquer um, `gerarProposta` lança `CamposFaltandoError` com a lista, a rota devolve 422 e nada é gravado no banco nem no Storage. Nunca pular campo vazio em silêncio: PDF com buraco onde deveria estar o nome do lead é pior do que PDF nenhum. Pela mesma razão, `resolverTemplateId` devolve `null` em vez de escolher uma arte padrão quando a idade falta.
6. Regerar PDF sobrescreve `{leadId}.pdf` no bucket `propostas` (URL estável para o link do WhatsApp). Preview no painel usa query param de cache-bust.
7. **O link público da proposta é `{APP_URL}/p/{slug}`** — 4 caracteres (707 mil combinações), coluna `slug` na tabela, gerada por `garantirSlug()` na primeira geração do PDF e nunca mais alterada (RF-14). Nunca devolver a URL crua do Supabase: esse link vai por WhatsApp e o lead lê o domínio. `APP_URL` errada em produção = link quebrado no celular de quem recebeu. A rota antiga `/proposta/{leadId}.pdf` continua viva porque links já enviados não podem morrer — mas não usar em código novo.
7b. **Os 4 caracteres são decisão consciente do owner (19/08/2026), não descuido.** O risco foi medido e apresentado: o espaço é varrível e um acerto expõe nome e data do evento. O owner manteve, pelo volume real (~3 leads/dia, trabalho artesanal que não escala) — nesse volume a colisão é desprezível e o espaço fica esparso. O que segura a porta é o **rate limit de 30/min por IP em `/p/[slug]`**: essa proteção não é opcional, é o que substitui o tamanho do slug. Nunca remover. Se um dia o volume mudar de ordem de grandeza, a correção é `TAMANHO_SLUG = 6` (594 milhões), e links antigos seguem valendo.

8. **A prévia da proposta no painel tem dois visualizadores, e isso é de propósito.** Acima de 640px é o `<iframe>` de sempre: o visualizador nativo dá rolagem contínua, zoom e impressão de graça. Abaixo de 640px ele não serve — o WebKit desenha o PDF dentro do iframe como uma miniatura de UMA página, com barra de rolagem própria e sem caminho para as outras páginas. No celular a prévia é desenhada por nós em canvas (`components/admin/PreviaProposta.tsx`, pdf.js), página inteira, uma por vez, com paginação embaixo, e com o link "Abrir PDF em tela cheia" (mesma URL, `target=_blank`): a 360px o corpo de 12 pt vira texto de ~5px, que serve de miniatura mas não de leitura. O componente é o mesmo da prévia do contrato. Não unificar nos dois lados: no desktop o card tem ~900px e a página A4 inteira sairia mais alta que a tela, o que exigiria encaixar também pela altura — problema que no celular não existe.
8b. O pdf.js entra por **import dinâmico** e só nessa tela: ele é grande e o bundle de `/formulario` é sagrado. Build `legacy` (já transpilado, roda em WebView antigo), e o arquivo é baixado com **um `fetch` só**, com os bytes entregues prontos ao `getDocument` — solto, o pdf.js fatia o PDF em vários range requests e `/p/{slug}` tem limite de 30/min por IP (7b).
8c. **Qual visualizador aparece é decidido por `clientWidth`, com `matchMedia` E `ResizeObserver` como gatilhos.** Só o `change` do `matchMedia` não basta: em emulação de dispositivo e em parte dos WebView a media não é reavaliada e o evento nunca chega, então girar o aparelho deixava o visualizador errado na tela.

## Contrato: gotchas obrigatórios

Nasceu da leitura dos 17 contratos-cliente da Mel (de 03/2025 a 08/2026) e de uma revisão jurídica verificada, em 29/09/2026. Os contratos reais ficam em `contratos-passados/`, que está no `.gitignore` e **nunca** vai para o repositório: têm CPF, endereço e e-mail de clientes, e este repositório é público.

1. **Núcleo determinístico, IA confinada.** Qualificação das partes, valores, extenso, parcelas, datas, cláusulas-padrão, numeração e remissões saem de código testado (`montar.ts`, `clausulas.ts`). A IA (Claude Fable 5.1, `claude-fable-5-1`, em `lib/contrato/ia.ts`) faz três coisas e só: extrair os dados de quem assina de um texto colado pela Mel; redigir a cláusula "DAS CONDIÇÕES ESPECIAIS" a partir das observações; e revisar o contrato devolvendo AVISOS. Nunca reescreve cláusula-padrão. Motivo: em contrato de adesão, contradição entre um texto livre e o núcleo é lida contra quem redigiu (CC art. 423, CDC art. 47), e número inventado por modelo é justamente o erro que ninguém percebe na revisão.
2. **O texto da IA passa por `validarTextoIa` antes de entrar.** Todo número (valor, data, hora, percentual, dias) é conferido **com a unidade** ("10%" não se prova com "10 dias") contra o contrato SEM cabeçalhos "CLÁUSULA N", numeração de item e remissões (senão 1 a 16 estariam sempre "provados"), contra os dados estruturados e contra as observações. Número por extenso ("trezentos reais", "dez por cento") e data "10/12" ou "10 de dezembro de 2026" também são conferidos (se a Mel anotou a data sem o ano, vale o ano que o contrato já usa); dígito e extenso que não batem ("5 (duas)") e marcador repetido ("[CONTRATANTE] [CONTRATANTE]") são problema. A lista de vedados (`TRECHOS_VEDADOS`, cada item com o motivo em texto humano) barra arbitragem, "não se responsabiliza", ônus da prova, multa, juros, perda ou não devolução de valores, "de pleno direito", "independentemente de notificação", foro/comarca, reajuste, renúncia... Cláusula `origem: "ia"` com problema **bloqueia o PDF** até a Mel editar — editar é ela assumir o texto. Pedido que tem campo próprio (parcelamento, valor, local, pacote) volta como aviso "use a seção X", e não como cláusula: o campo gera o texto certo, a cláusula especial geraria uma segunda versão dele.
3. **A IA não recebe CPF, CNPJ, endereço, e-mail, telefone nem nomes** (contratante, representante, anuente, homenageado). `anonimizar.ts` troca por marcadores e desfaz na volta, comparando sem acento e sem caixa ("R. das Acacias", "ANA", "jd. primavera"), e antes disso varre QUALQUER e-mail, CPF, CNPJ e telefone, de quem quer que seja (o pai que paga, colado nas observações). Local de evento, making of ou ensaio que é espaço público vai inteiro (como a qualificação da CONTRATADA); o que tem dado pessoal ou diz de quem é a casa ("casa da Ana") passa pela troca. `dadosPessoaisNoTexto` confere o resultado com a mesma régua e, se algo sobrou, a IA não é chamada. Cada cláusula chega à IA com a origem no cabeçalho ("padrão aprovado", "redigida pela IA", "editada no painel"): no padrão aprovado a revisão só aponta o que depende DESTE contrato — estilo e lacuna genérica do modelo se repetiriam em todo contrato e esconderiam os avisos que importam. A extração é a única exceção, e é inevitável: ela recebe o texto que a Mel colou. Sem `ANTHROPIC_API_KEY` tudo funciona menos a IA — o contrato padrão sai, e as observações viram aviso "escreva a cláusula no editor". Falha da IA também não trava a Mel: a redação sai sem a cláusula especial, com aviso.
4. **Quem assina nunca é pré-preenchido com `respostas.nome` em evento de menor**: quem preencheu o formulário pode ser a própria debutante, e contrato assinado por menor de 16 é nulo (CC arts. 3º e 166). "Evento de menor" = debutante OU aniversário com idade < 18 — **nunca decidido pelo `TemplateId`**, porque `aniversario_adulto` cobre 15+ e inclui 15-17. Nesse caso a qualificação declara o vínculo (mãe, pai, responsável legal) e a autorização de imagem inclui o menor pela representação; com 16-17 anos o aniversariante entra como ANUENTE, assistido. O anuente também é o caminho para cobrir a imagem do outro noivo. **Empresa (PJ) não autoriza a imagem de ninguém**: fora do corporativo, contratante PJ gera aviso "atencao" pedindo o homenageado como anuente (em evento de menor, o responsável legal, que então autoriza a própria imagem e a do menor). O schema tem UM anuente: em casamento contratado por empresa, o aviso diz que o outro noivo segue sem autorização. `anuenteEhHomenageado` só olha o papel que COMEÇA pelo do homenageado — "pai do aniversariante" não é o aniversariante.
5. **Gênero gramatical é campo explícito escolhido pela Mel** ("Sra./Sr."), nunca inferido do nome, nem pela IA. 4 dos 17 contratos antigos erraram a concordância ("brasileiro, inscrita").
6. **O contrato é o único lugar do sistema em que preço vira número** (exceção à regra 6). O catálogo — `PACOTES` de `precos.ts` mais os adicionais de `catalogo.ts`, transcritos das artes — só PRÉ-PREENCHE; quem confirma o valor é a Mel. A tabela sugerida é a do ano do evento, mas ela pode escolher outra: proposta aceita antes do reajuste vale o preço da proposta (CDC art. 40 §2º), e dois contratos de 2027 foram assinados na tabela 2026. Dinheiro em centavos inteiros; o resíduo do arredondamento cai na última parcela; o extenso sai de `extenso.ts`, testado contra todos os valores dos contratos antigos.
7. **Decisões do owner sobre o texto (29/09/2026), não reabrir sem pedido:** SEM cláusula de arrependimento de 7 dias; SEM cláusula informativa de LGPD; COM reciprocidade (se a Mel faltar por culpa dela, devolve tudo mais o valor do sinal), COM ressalva de correção de erro da Mel sem custo, COM cláusula de acesso à conta do Instagram; foro PF = comarca do domicílio da CONTRATANTE, PJ = Monte Mor/SP; portfólio incluído na autorização de imagem, **inclusive anúncios pagos**. Corpo do PDF em 12 pt e negrito só nas frases limitativas e na autorização de imagem (CDC art. 54 §§3º e 4º) — negritar tudo anularia o destaque. **Pendentes com o owner, não implementar por conta própria** (mudam condição comercial): ressalva de caso fortuito/força maior na retenção do sinal (C05 do jurídico; hoje a desistência retém o sinal e devolve o que foi pago além dele), o que acontece com o saldo não pago no prazo (C14), prazo final da "finalização da cobertura" no tempo real, e a cláusula em que a empresa do corporativo responde pelas autorizações de imagem de convidados e funcionários (C20).
8. **Dados da CONTRATADA são constante** (`contratada.ts`), inclusive o endereço residencial da Mel — decisão do owner em 29/09/2026, sabendo que o repositório é público. Mudou endereço, e-mail ou PIX: muda ali, e só os contratos gerados dali em diante saem com o dado novo.
9. **Contrato é PII.** Tabela `contratos` com RLS, zero policies e revoke de anon/authenticated; bucket PRIVADO `contratos` (só PDF, até 10 MB). O PDF só sai por `/api/admin/leads/[id]/contrato/arquivo`, com sessão e `no-store` — nunca por `/p/{slug}`, nunca por URL do Storage. As colunas internas (`pdf_path`, `assinatura_token`, `posicoes_assinatura`, `assinado_path`, `trilha_path`) nunca vão ao navegador: o select do painel é explícito em `lib/supabase/contratos.ts`. Log com id e código, nunca CPF, e-mail ou payload.
10. **Excluir o lead apaga a pasta `{leadId}/` do bucket `contratos` ANTES da linha.** A linha de `contratos` cai por cascade; o arquivo não. Falha no Storage aborta a exclusão, pela mesma razão do PDF da proposta: "excluído" com o arquivo ainda no bucket é mentira.
11. **Assinatura pela API REST da iLoveAPI (iLovePDF)**, atrás de `ProvedorAssinatura` (`lib/assinatura/`), com `ASSINATURA_DRY_RUN=1` como padrão de desenvolvimento — mesma lógica do `MailAdapter`. O MCP do iLovePDF não serve para isto: não tem assinatura e roda localmente. **Os 2.500 créditos grátis da iLoveAPI não valem para assinatura** (o `start/sign` responde "You don't have enough signatures"); sem pacote de assinatura comprado, o envio responde 503 com texto humano e o resto do contrato funciona. O envio é sempre clique da Mel (regra 4).
12. **O que foi para assinatura não muda.** Em `enviado` e `assinado` o texto trava (409 em salvar, redigir, editar e regerar). O PDF assinado e a trilha de auditoria ficam num caminho próprio de cada envio e nunca são sobrescritos — ao contrário da proposta (RF-14). Cancelar o envio, ou a plataforma devolver recusado/expirado, volta para `pdf_gerado`. Se a plataforma responde 404 no cancelamento E na consulta, ou o token gravado não se lê, "Cancelar envio" encerra o envio **só no sistema** (200 com `pedidoInexistente` e um `aviso` que a tela mostra no lugar do "Envio cancelado"); a consulta nesse caso responde 409 apontando o "Cancelar envio" e **não** destrava sozinha, porque roda ao abrir a página e encerrar envio é decisão da Mel. Contratante PJ vai à plataforma com o nome do REPRESENTANTE (quem assina de fato); a razão social fica só no bloco impresso.
12b. **Escrita que depende do que foi lido é guardada por `updated_at`** (`CondicaoEscrita.atualizadoEm`, em `_escrita.ts`): salvar texto editado, gravar o PDF, gravar a redação da IA e reservar o envio. Duas abas intercaladas deixavam `pdf_gerado` com o PDF de um texto e o painel mostrando outro — e o envio mandava o PDF velho. Conflito responde 409 "O contrato foi alterado em outra aba. Recarregue a página.", e editar o texto SEMPRE zera o PDF. No painel, link interno com alteração não salva pede confirmação por um listener de clique em captura: o App Router não dispara `beforeunload`.
13. **Contrato não mexe em `leads.status` nem em `enviado_em`**, que alimenta a cobrança de 7/30 dias. Com o contrato assinado, o painel oferece "Mover lead para Virou cliente", que usa o PATCH de status de sempre (e dispara o `VirouCliente` da regra 8b).
14. As rotas de IA têm `maxDuration = 300` e usam streaming: o Fable pode levar minutos. Redigir e revisar são duas requisições separadas, e cada uma cabe no teto sozinha. O prazo vai como `AbortSignal.timeout` nas opções do `stream` (250 s com 1 retentativa em redigir e revisar, 120 s com 2 na extração): o `timeout` do SDK só cobre até chegarem os cabeçalhos e deixava o corpo do stream sem limite nenhum. Estourado, vira `IaError` "timeout" e a redação sai sem a cláusula especial, com aviso.
15. `npm run contrato:verificar` (offline, sem banco e sem IA) monta e renderiza um cenário por arte × pacote, mais PJ, anuente, tempo real, 15/15/70, quitado etc., em `.contrato-verificacao/`, e falha com "{{", "undefined", numeração quebrada ou assinatura fora da página. Cada cenário pode exigir trechos do texto e avisos (`deveConter`, `naoDeveConter`, avisos esperados). `npm run e2e:contrato -- <base>` exercita a API contra o banco real, com admin e lead temporários que ele mesmo apaga. **Passe a base**: a porta 3000 desta máquina é de outro projeto. Só roda contra base local (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost`) sem `--permitir-remoto`, e quem diz se a assinatura está em dry run é o SERVIDOR (`assinaturaDryRun` no GET do contrato), nunca o `.env` de quem roda o script: fora do dry run o envio não roda e o script termina vermelho.
16. **O escopo sabe QUANTO TEMPO o auxiliar trabalha** (`escopoEfetivo(servico, templateId)` → `minutosAuxiliar`). Storymaker por evento é equipe de dois a cobertura inteira; por hora, só vira equipe de dois se as horas cobrirem a cobertura — antes disso objeto, serviços e alimentação dizem "por até N horas". O parágrafo dos making ofs "impossibilitando a realização simultânea" só entra se nenhum adicional indicar segunda pessoa (inclusive o livre que fala em storymaker, auxiliar ou simultâneo), com aviso para conferir a logística. A unidade de cobrança (`unidadeDoAdicional`) é UMA função, da montagem, que o painel reusa: o campo de horas aparece exatamente onde o contrato diz "por hora".
17. **Ensaio fotográfico (Pacote Luxo da debutante) tem data, local e horário próprios** (`evento.ensaioData/ensaioLocal/ensaioHorario`, vazio = A DEFINIR, com agendamento de comum acordo e 10 dias de antecedência). Acontece ANTES do evento (depois é faltante; o mesmo dia é aceito), e o "Tempo de serviço no dia do evento" não soma o ensaio. O corporativo é entrega em tempo real nos três pacotes (a arte promete stories durante o evento), o que traz a cláusula das condições técnicas.
18. **Pagamento tem quatro opções e quase nenhum campo** (pedido do owner em 30/09/2026): "30% + 70%" (o padrão das artes), "Metade-metade" (50% de sinal na assinatura + 50% até 10 dias antes do evento), "Já pago" e "Personalizado". O editor de parcelas saiu da tela; os modelos prontos aparecem como resumo. 15/15/70 e "tudo na assinatura" continuam sendo dados válidos (contrato salvo antes segue montando), só não são mais botão.
19. **"Personalizado" é texto livre que a IA INTERPRETA, e o código escreve.** A Mel escreve do jeito dela ("8 vezes de R$ 100", "tudo depois que eu entregar"). Na redação, `interpretarPagamento` transforma o texto em grupos de parcelas (quantidade, valor em reais OU percentual, frase de vencimento, se é sinal, se o vencimento é determinável), e `calcularPersonalizado` faz a conta em centavos e a cláusula sai com valores e extenso do código. O modelo só transcreve: a soma que não bate com o total NÃO é corrigida — vira problema que bloqueia o PDF ("as parcelas somam R$ 800,00, mas o total é R$ 2.470,00"), assim como parcela sem vencimento determinável. Vencimento preso à entrega do material conta como determinável (o contrato fixa o prazo de entrega). Sinal só onde a Mel disse entrada/sinal/reserva; sem sinal, a desistência sai sem os itens de retenção e a montagem avisa. A interpretação é guardada com o texto de que saiu (`textoFonte`): texto mudado = interpretação velha, e só o SERVIDOR grava interpretação (`manterInterpretacao` descarta a que vem do navegador).
20. **Logo da Mel no topo da primeira página do contrato**, centrado, 150 pt de largura (tamanho de timbrado, abaixo do peso do título). Vetorial, desenhado pelo pdf-lib a partir de `lib/marca/logo.ts` — a MESMA fonte de traçados do `LogoMel.tsx` do painel. Nunca copiar os paths para outro lugar.

## LP de venda (`/casamento`): gotchas obrigatórios

Pedida pelo owner em 01/10/2026: destino dos anúncios pagos de casamento no Instagram. Os Reels reais da Mel são a prova; todo CTA leva ao formulário em modo casamento (5f).

1. **Decisões do owner, não reabrir sem pedido:** identidade completa da marca só aqui (ver "Identidade visual do SITE"); Reels **mudos no autoplay e com som ao tocar** (o risco das trilhas licenciadas só para o Instagram foi apresentado e o owner manteve); **nenhum nome de casal e nenhum depoimento** (cada vídeo leva o espaço e o mês); **sem preço** (regra 6: o valor sai na proposta). **Posicionamento, revisado pelo owner em 03/10/2026:** o serviço é o REGISTRO pelo celular, em vídeos para o casal guardar e rever; publicar nos stories é opção do casal, nunca a promessa principal. A copy anterior ("Vocês vivem o casamento. Eu conto tudo nos stories.") afastava quem quer contratar sem postar, e a comparação com o fotógrafo punha o valor da Mel na rede social. O CTA principal é "Consultar nossa data" (hero, pacotes, barra fixa, visualizador), e o botão não consulta agenda nenhuma (regra "Nunca fazer"): quem diz se a data está livre é a Mel, na conversa. A frase de apoio embaixo do CTA do hero saiu a pedido do owner (03/10/2026); a do CTA final continua. **Hero, também de 03/10/2026:** nada de vídeo ATRÁS do texto — o título sobre as pétalas claras não se lia. O vídeo é um quadro 4:3 recortado nos noivos (`HERO.recorteY` em `reels.ts`), com visor de câmera (REC, contador, cantos) desenhado por cima em `HeroVideo`; o texto fica no escuro liso. A ordem é a do owner: rótulo, título, vídeo, texto de apoio, CTA. O contador conta o tempo ASSISTIDO, não o `currentTime`: o teaser tem 6 s em loop, e um contador que volta a zero entregaria o loop.
2. **Toda frase tem lastro.** Pacotes e prazos saem de `app/casamento/conteudo.ts`: os bullets do `itensArte` MENOS o de prazo, e o prazo montado do `escopo` do contrato. A arte diz "até 5 dias úteis" para tudo, mas o contrato dá 5 para os stories e 7 para o Reels e o material; numa página de anúncio a oferta vincula (CDC art. 30), então a LP segue o contrato. Os números das garantias e do FAQ (reserva de 30%, saldo até 10 dias antes, 48 h sem internet, 6 meses de link, 5 dias úteis de correção, 10 dias de devolução) saem de `condicoesDaLp()`: reserva e saldo do modelo de pagamento "30/70" do contrato, e o resto conferido pelo `conteudo.test.ts` contra o TEXTO de `clausulas.ts` — mudou a cláusula sem mudar a LP, o teste quebra. Os espaços vêm das legendas dos Reels, e o "Desde 2024" da faixa sob o hero sai de `ANO_PRIMEIRO_CASAMENTO` (o primeiro casamento publicado no Instagram da Mel, nov/2024). "Mais de 200 celebrações" (no hero e na apresentação da Mel) é o único número AFIRMADO pelo owner (03/10/2026, todas as categorias), e mora em `CELEBRACOES_MAIS_DE`. Nunca escrever prazo, número ou preço à mão em `page.tsx`: o mesmo teste lê o arquivo e falha com `R$` ou com número seguido de dias, horas, meses, semanas ou `%`, em algarismo ou por extenso (a copy de 03/10/2026 chegou com "sete dias úteis", que passava pela versão só de algarismos). O catálogo é lido só no servidor: para as ilhas do navegador descem strings, senão os preços em centavos iriam no payload do HTML.
3. **Mídia:** `app/casamento/reels.ts` é a ESCOLHA (id do Reel, espaço, mês, trecho de pico do preview); `npm run lp:reels` gera, a partir de `.lp-bruto/<id>.mp4` (baixado com yt-dlp, fora do git), o Reel completo (540x960), o preview mudo de 4-6 s, o pôster e, do hero, o teaser e o pôster no recorte 4:3 de 720x540 (mudo, até 700 KiB; o LCP é o pôster, não o vídeo) e a foto vertical da imagem de compartilhamento (`fotoOg`), em `public/midia/casamento/`, e reescreve `midia.gerado.ts`. Os nomes levam o hash do conteúdo porque `/midia/*` é servido como immutable (`next.config.ts`). **O immutable nunca pode casar com a página**: `/casamento/:path*` casaria com o próprio `/casamento`, e o navegador do Instagram guardaria o HTML por um ano, apontando para chunks que somem no deploy seguinte. `reels.test.ts` guarda manifesto, hash, orçamento de peso e essa regra. Casamento novo = baixar, uma linha no manifesto e rodar o script. **O script só recodifica o que mudou**: cada arquivo guarda em `midia.gerado.ts` a `origem` (áudio do Reel; trecho do preview e do pôster; Reel, trecho e recorte do hero) e, batendo, fica o mesmo. Isso não é otimização: recodificar NÃO sai idêntico byte a byte (o x264 com várias threads varia entre execuções, medido em 03/10/2026), e uma execução que refizesse tudo trocaria o hash dos dez vídeos, ~96 MB novos no histórico de um repositório público e o cache immutable de quem já assistiu jogado fora. `--refazer` força tudo, de propósito. O `reels.test.ts` confere a `origem` contra o manifesto: mudou um trecho e esqueceu o script, o teste quebra. Antes de commitar mídia, `git status public/midia` tem que mostrar só o que você quis mudar. Tirar o som = `lp:reels -- --sem-audio`, mas o repositório é público: o áudio já commitado continua no histórico do git.
4. **A galeria toca só o preview, um por vez** (o card mais visível, com a galeria na tela, sem `prefers-reduced-motion` nem economia de dados). O Reel inteiro só carrega no toque. Ao sair do card o `src` é removido, não só pausado: `pause()` não para o download nem libera o decodificador, e muito vídeo vivo é o que faz o WebKit matar a aba. O teaser do hero pausa sozinho fora da tela (IntersectionObserver) e com o visualizador aberto: a pausa automática de vídeo invisível do navegador só vale para quem tem o atributo `autoplay`, e ele toca por `play()`.
5. **Visualizador em tela cheia: UM `<video>` só, e o play com som acontece DENTRO do toque no card** (`abrir`, síncrono). O WebKit pausa vídeo que ganha som fora de gesto, e o fim de um swipe não é gesto; o elemento que já tocou com som num toque fica liberado, e trocar de casamento vira trocar o `src`. **Só `NotAllowedError` é "som recusado"**: trocar o `src` com um `play()` pendente rejeita a promise antiga com `AbortError`, e tratá-lo como recusa deixava mudo o Reel para onde a pessoa deslizou. Fechar limpa os timers do swipe e do "segurar" (sem isso, o próximo Reel tocava com som por baixo da página fechada). O pôster leva `-webkit-touch-callout: none`: sem isso, segurar o dedo para pausar abre o menu de imagem do iOS. Os slides são pôsteres, o vídeo fica fixo por cima e só aparece com o slide parado. Histórico: um `pushState` sem URL ao abrir, X e Esc chamam `history.back()`, o `popstate` fecha; o CTA de dentro usa `location.replace`, para o voltar do formulário cair na LP e não num visualizador fechado. Fica sempre montado, escondido com `visibility` (o `estilo:verificar` precisa enxergar os controles).
6. **A página é ESTÁTICA** (HTML no CDN, TTFB mínimo no 4G). Nada lê a URL no servidor: a query do anúncio (`fbclid`, `utm_*`) entra nos CTAs pelo navegador, primeiro por um script inline no fim da página (`a[data-cta]`), que roda ANTES da hidratação — no 4G o lead toca no botão do hero antes de o React acordar, e o `<a>` estático sem a query faria o lead nascer sem nada que o ligasse ao anúncio —, e de novo no mount e no clique do `CtaFormulario`. O `?reel=<id>` do anúncio põe o Reel do criativo em primeiro na galeria. CTA é `<a>` puro, nunca `next/link`: o `next/script` guarda o snippet do Pixel pelo id, e a navegação client-side deixaria o formulário sem PageView. O `href` é sempre expressão (`hrefFormulario`), porque o lint `no-html-link-for-pages` acusa `<a>` com rota literal.

A rota dinâmica do `next/og` só devolve PNG, e com a foto passava de 550 KB: o WhatsApp costuma descartar prévia acima de ~300 KB. Rode de novo quando mudar o título ou o teaser do hero. ### Identidade visual do SITE (não do PDF)

**As duas identidades são separadas e não se contaminam.** O site tem a paleta abaixo; o PDF tem a arte do Figma, com as cores e fontes que a Mel desenhou lá. Unificar as duas seria destruir a arte — nunca mexer em `assets/templates/` ou nas cores de `lib/pdf/templates.config.ts` a pretexto de "seguir a paleta".

- **Paleta: duas cores.** O escuro da marca (`#20130A`) e `#F1F1F1`, em `--marca-escuro` e `--marca-claro`. Branco entra só como superfície de card. Tom intermediário se deriva com opacidade (`rgb(var(--marca-escuro-rgb) / 12%)`), nunca acrescentando um hex novo — por isso existe `--marca-escuro-rgb`, os componentes soltos da mesma tinta.
- **A identidade da Mel (Figma, frame `7120:556`) tem quatro tons**: `#20130A` (escuro, e a cor do logo), `#4D2B22`, `#823B25` (terracota) e `#CBAD95` (areia), mais um creme `#F0E0C7`. O app usa **dois**: o escuro e `#F1F1F1`. A terracota entra num lugar só, o **anel de foco** (`--ring`) — é o acento da marca onde ele aparece em toda tela sem repintar nada. Os outros dois ficam registrados no comentário do `globals.css` para ninguém inventar um marrom diferente; não estão em uso.
- **O claro continua `#F1F1F1`, e não o creme da marca.** Troca pedida pelo owner em 29/08/2026 foi só das cores **escuras** (preto → `#20130A`), para o painel seguir clean. Trocar o fundo pelo creme é decisão nova, não consequência desta.
- **`--muted-foreground` é 65%, não 60%.** O marrom é mais claro que o preto: a 60% caía para 4,56:1 sobre `#F1F1F1` — passa no AA, mas sem folga. A 65% dá 5,37:1. Ao mexer na tinta escura, refaça essa conta.
- **O logo é `components/marca/LogoMel.tsx`**, SVG inline com `fill="currentColor"` (o arquivo original vinha com `#20130A` fixo). Inline e não `<img>`: aparece no cabeçalho de toda tela autenticada, e uma requisição a mais atrasaria a primeira pintura. Altura por classe (`h-7` = 28px), largura automática pelo viewBox 274x38.
- **A regra das duas cores vale para as telas do LEAD** (`/formulario`, `/p/[slug]`, `/`). **Exceção: a LP de venda `/casamento` usa a identidade COMPLETA** (escuro, `#4D2B22`, terracota, areia `#CBAD95` e creme `#F0E0C7`), decisão do owner em 01/10/2026 — página de venda pede o calor da marca. Os três tons extras vivem em `.lp-casamento` (`globals.css`), não no `:root`: fora da LP, `bg-marca-creme` não pinta nada. O `estilo:verificar` aplica a paleta POR URL: ampla em `/casamento`, estrita nas outras. Nas faixas escuras da LP o anel de foco vira creme (`.lp-escuro`), porque terracota sobre o escuro fica a 2,2:1. O **painel interno** usa também as cores de status do quadro — slate/âmbar/sky/emerald —, definidas só em `CLASSE_STATUS`/`TEMA_COLUNA` (`lib/admin/rotulos.ts`). Decisão do owner em 20/08/2026, ao pedir o kanban com "visual Notion". Já havia precedente não documentado (`emerald-100` no badge de enviado, `amber-50`/`emerald-50` nos avisos do detalhe). As classes são **literais**: `bg-${cor}-50` some do CSS porque o scanner do Tailwind v4 não lê string interpolada. E **não** apontar `estilo:verificar` para `/admin` — ele falharia por desenho, além de exigir sessão.
- **Fonte: DM Sans em tudo**, servida de `assets/fonts/` via `next/font/local` (não do Google Fonts — ida a terceiro atrasa o LCP). `--font-sans`, `--font-heading` e `--font-mono` apontam todos para ela.
- **Tracking:** títulos, botões e utilitários de peso (`font-semibold/bold/black`) levam `letter-spacing: -0.3px`. É CSS do site apenas — o texto do PDF é desenhado pelo pdf-lib e não passa por aqui.
- **Cursor de mão em tudo que se clica**, sem exceção: botão, link, item de menu, opção de escolha, checkbox, radio, select. Desabilitado usa `not-allowed`. Campo de texto (inclusive data e hora) fica com o cursor de digitação — ali a mão sugeriria botão. A regra é global, em `@layer base`; nunca reintroduzir `cursor-default` num componente (o utilitário vence a camada base e foi o que o shadcn trouxe por padrão). Motivo de existir: o **Tailwind v4 mudou o padrão do `button` de `pointer` para `default`**, então sem a regra o sistema inteiro perde a dica de clicabilidade.
- **Raio: 6px em tudo.** Toda a escala `--radius-sm..4xl` aponta para `--radius`. Não usar `rounded-full`: mudar o raio do app inteiro deve ser mexer em uma linha só.
- `npm run estilo:verificar` (com `npm run dev` em outro terminal) checa cinco coisas no DOM renderizado: raio, fonte, paleta, **cursor de todo clicável** e ausência de scroll horizontal em 360px. Julgar por screenshot não serve — 6px num print em 2x parece 12px.
- **O verificador não clica**: do formulário (uma SPA) ele só enxerga a PRIMEIRA tela de cada URL. (Desde que `/orcamento` existe, a tela de categoria é a primeira de uma URL e entra na checagem.) Foi assim que `border-foreground/25` (no `OpcaoEscolha`, tela de categoria) conviveu meses sem ser checado e só acusou quando a mesma classe chegou à abertura. E o que ele acusou não era cor nova: os modificadores de opacidade do Tailwind v4 (`/25`, `/70`) compilam para `color-mix(in oklab, ...)`, então o `getComputedStyle` devolve `oklab(...)` e não `rgba(...)`. O script compara os tons da marca também em oklab, por valor e com tolerância. Os tons ficam numa tabela só (`TOM`, com hex, rgb e oklab) e `paletaDaUrl` escolhe quais valem em cada página: ao acrescentar um tom, ponha as três notações ali. Ele também rola a página até o fim antes de inspecionar (conteúdo montado por IntersectionObserver), e inspeciona elemento com `visibility: hidden` — por isso o visualizador de Reels e a barra fixa da LP ficam sempre montados.
- `chrome --headless --window-size=360,x` **não** dá viewport de 360px (o Chrome tem largura mínima de janela e a imagem sai só recortada, simulando um estouro que não existe). Use `npm run screenshot -- <url> <saida.png> 360`, que emula via CDP.

## Workflow

- Commits pequenos, mensagens em inglês, padrão convencional (`feat:`, `fix:`, `chore:`).
- Mudança de arte (PDFs base ou coordenadas em `templates.config.ts`): PR dedicada contendo só isso.
- Feature só está pronta depois de rodar o cenário da Definition of Done (PRD seção 18) para a categoria afetada.
- Antes de deploy final: testar manualmente as 4 categorias e as 5 artes (aniversário com idade ≤14 e ≥15), incluindo a ramificação `making_of` com "Sim" e com "Não", e a retomada de lead incompleto. Com mais de uma tabela viva, testar também um evento de cada ano de tabela — é a única forma de ver o preço certo saindo no PDF, já que ele é imagem e nenhum teste o lê.
- `npm run pdf:verificar` cobre o cruzamento **arte × tabela de preço** (5 artes × N tabelas), e falha se alguma combinação ficar sem cenário. Arte ou tabela nova sem cenário = script vermelho, de propósito: senão dá para acrescentar uma arte, ou um ano inteiro de preço, e nunca abri-los em teste nenhum. Enquanto uma tabela não tiver as 5 artes publicadas, ele lista os arquivos que faltam — vermelho esperado, não regressão.
- **Nunca rodar `npm run build` com o `npm run dev` no ar**: os dois escrevem em `.next` e o dev server passa a devolver 500 com `ENOENT ..._buildManifest.js.tmp`. A correção é parar o dev, `rm -rf .next` e subir de novo.
- Cobrança de 7/30 dias: `lib/admin/lembretes.test.ts` cobre as fronteiras (6/7/29/30 dias), o "só dentro de Enviado" e o pulo direto para os 30 num lead de mês e meio. Testar isso à mão exigiria esperar uma semana — as fronteiras são o único lugar onde um off-by-one aparece, e ali ele custa uma cobrança irritante no 6º dia ou uma semana perdida no 8º.
- Quadro de leads: `npm run e2e:quadro` (API, rápido) e `npm run e2e:arraste` (arraste real via CDP, precisa do Chrome). Os dois criam admin e leads temporários e limpam no fim. O `e2e:quadro` cobre também o "Lembrar por e-mail" e o `/continuar`: as recusas rodam contra qualquer base, mas o ENVIO só contra servidor local com `MAIL_DRY_RUN=1` no `.env.local`, para um endereço `.invalid`, e o servidor ainda tem de confirmar o dry run na resposta.
- Ao corrigir um bug causado por premissa errada sobre o projeto, registrar a regra correta neste arquivo na mesma PR.
