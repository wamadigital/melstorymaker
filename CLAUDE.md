# CLAUDE.md | Sistema de Propostas Mel Simão

Contrato operacional deste repo. A especificação completa (requisitos, árvore do formulário, critérios de aceite) está em `PRD.md`, que é a fonte de verdade do produto. Este arquivo define como trabalhar aqui. Em conflito entre os dois, o PRD define O QUE, este arquivo define COMO.

## Contexto em 2 linhas

MVP: lead preenche formulário multi-etapas estilo Typeform em `/formulario`, sistema gera PDF fiel à arte do Figma, Mel aprova no painel `/admin` e envia por e-mail + WhatsApp. O anúncio de casamento chega antes pela LP de venda `/casamento`. O MVP original usava free tiers; desde 15/10/2026 o runtime de WhatsApp funciona na Railway Hobby, com limites financeiros aprovados abaixo. Produção: `https://melstorymaker.com.br` (DNS gerenciado no Registro.br).

## Stack (travada, não sugerir alternativas)

- Next.js 14+ App Router, TypeScript strict
- Tailwind + shadcn/ui + Framer Motion (só nas transições do form)
- Supabase: Postgres, Auth, Storage
- pdf-lib + @pdf-lib/fontkit
- Nodemailer + Gmail SMTP, atrás de `MailAdapter`
- Deploy web: Vercel; bridge, MCP stdio e worker WhatsApp: Railway Hobby

## Comandos

```bash
npm run dev          # ambiente local
npm run build        # build de produção (rodar antes de todo commit relevante)
npm run lint         # ESLint
npx tsc --noEmit     # checagem de tipos
npm run lp:reels     # mídia da LP /casamento (Reels brutos > vídeo, preview, pôster); só refaz o que mudou
npm run lp:og        # imagem de compartilhamento da LP
```

Schema do banco: aplicar `supabase/schema.sql` manualmente no SQL Editor do Supabase. Não usar migrations automáticas neste MVP.

## PDF: gotchas obrigatórios

1. pdf-lib usa origem no canto INFERIOR esquerdo da página. Converter coordenadas vindas do Figma (origem superior esquerda): `y_pdf = alturaPagina - y_figma - tamanhoFonte`.
2. Chamar `pdfDoc.registerFontkit(fontkit)` ANTES de embutir qualquer fonte custom.
3. Campo com `maxLargura`: reduzir o tamanho da fonte proporcionalmente até caber. Nunca quebrar linha em campo de nome.
4. Criar a rota de calibração `/admin/debug-template?template=X` (grid de coordenadas a cada 20pt sobre o PDF base) ANTES de calibrar o primeiro template. Calibrar sem ela é proibido. O parâmetro é o `TemplateId`, não a categoria: `aniversario` sozinho é ambíguo. Aceita também `&tabela=` (padrão: a base) — cada tabela tem PDF base próprio, e o grid sobre a arte de 2026 não prova nada sobre a de 2027.
4b. **Preparo da arte** (mudança de arte = PR dedicada): esvaziar os placeholders no Figma (manter só `Olá,` no bloco de saudação, ocultar o cabeçalho), exportar cada frame com `download_assets` em PDF e rodar `npm run arte:preparar -- <template> <tabela> <pasta>`. A **tabela é posicional e obrigatória**, não flag com padrão: errá-la sobrescreve em silêncio a arte de um ano com as páginas de outro. O Ghostscript roda SÓ nesse preparo, rasterizando cada página; em produção continua apenas pdf-lib. **Depois de mudar a arte, os PDFs já gerados continuam com a arte velha** — só saem atualizados quando a Mel clicar em Gerar PDF de novo (o link não muda, RF-14).
4c. As cinco capas compartilham o mesmo desenho, montado por `camposCapa()` em `templates.config.ts`. Arte nova = uma chamada, variando a composição do cabeçalho e o `x` do nome.
4d. **A arte base é RASTERIZADA: um JPEG por página, sobre página A4 (595x842 pt).** O export do Figma é vetorial e trazia ~96 mil operações de path (o padrão topográfico) + 51 grupos de transparência; o visualizador de PDF do celular estourava o orçamento de renderização e pintava a página **branca**, só mostrando o conteúdo depois de um zoom que o obrigava a redesenhar em blocos. Reduzir a página para A4 sozinho **não resolveu** — foi preciso rasterizar. Resultado: de 96.405 operações de path para 10, e 12,05 → 3,25 MB no conjunto das 5 artes.
4e. O texto que o lead lê como DADO (nome, data, cabeçalho) **não** está no raster: é desenhado pelo pdf-lib em runtime, continua vetorial e nítido em qualquer zoom. O que virou pixel é o texto *da arte* — títulos, corpo, preços. Trade-off aceito pelo owner em 19/08/2026, tendo como alternativa o PDF branco no celular.
4f. `escala: ESCALA_ARTE` (595/1240) em todas as artes, nunca `1`: as coordenadas do config continuam sendo as do painel do Figma e a escala multiplica x, y e tamanho de fonte no `gerar.ts`. Verificação: gere e meça: o cabeçalho do casamento deve terminar em x≈552 pt.
4g. A peça é **100% digital** — ninguém imprime. O alvo é a tela: `--altura 2000` px por página (~171 DPI em A4). Subiu de 1280 (~109 DPI) em 20/08/2026 porque naquela resolução o texto *da arte* ficava visivelmente mole ao dar zoom. Como a arte inteira é imagem, essa altura é o único controle de nitidez que resta. `arte:preparar -- <arte> <pasta> [--altura PX] [--qualidade N]`.
4h. **O caminho vetorial já foi tentado e não resolve — não repetir.** Converter só as ondas em PNG (feito no Figma e que continua valendo) zerou os grupos de transparência (51 → 0), mas os paths caíram apenas de 96.405 para 78.027, e no celular a página continuou branca. A razão: **o Figma exporta texto como CONTORNO, sem fonte embutida** (zero `/FontFile` no PDF). Cada letra vira dezenas de curvas e só o corpo de texto responde por ~12 mil operações por página — nada que o Ghostscript alcance.
4i. As ondas do padrão topográfico **já estão como PNG dentro do Figma**, convertidas em 19/08/2026 com o vetor original oculto ao lado (`ondas (vetor original, oculto)`). Não desfazer: era o que sustentava os 51 grupos de transparência. Ao mexer na arte, o critério de "onda" é ≥3000 segmentos de path **e zero nós de texto** — sem a segunda condição o bloco de contato da Mel (telefone, e-mail, CNPJ) é confundido com decoração.
4j. **Tabela de preço nova NÃO se prepara do zero: deriva-se da anterior.** `npm run arte:derivar -- <arte> <tabelaOrigem> <tabelaDestino> <pasta>` copia a arte já publicada página por página e troca só as que estão na pasta, nomeadas pelo NÚMERO da página (`03.pdf` troca a terceira). Entre duas tabelas muda o preço e mais nada — remontar tudo a partir de um reexport abriria espaço para as páginas comuns divergirem por algo que ninguém pediu (uma foto trocada no Figma desde o último preparo). Derivando, a única diferença possível é a pretendida, e dá para **provar**: rasterize as duas artes e compare página a página; só a de Pacotes pode diferir. Foi assim que a tabela 2027 entrou, em 28/08/2026.
4k. Os parâmetros de raster (altura 2000, qualidade 82, A4) moram em `scripts/arte-raster.ts`, **compartilhados** por `arte:preparar` e `arte:derivar`. Nunca duplicar: se divergirem, a página trocada sai com nitidez diferente das vizinhas dentro do mesmo PDF, e como a arte inteira é imagem isso aparece na tela do lead.
4l. No Figma, cada tabela tem seu próprio frame de Pacotes, nomeado `<arte>_NN_tabela<ano>` (ex.: `casamento_04_tabela2027`), logo abaixo do original na mesma coluna. **Não editar o preço no frame de 2026 para gerar o de 2027** — os dois precisam continuar existindo, senão a arte da tabela antiga deixa de ser reproduzível. Os preços têm largura automática e o dígito do DM Sans não é tabular (o `0` mede ~30px, o `1` ~14px): ao trocar o número, ancore pela **borda direita** (`x = direitaAntiga - larguraNova`) e desloque o nó `R$` mantendo o mesmo respiro — fora do casamento, onde o `R$` faz parte do mesmo nó de texto.
5. Formatação sempre via `lib/pdf/formatadores.ts`: **data em DD/MM/AAAA** ("14/03/2026") em TODOS os PDFs, hora no padrão "19h30". O formatador `data_extenso` continua disponível no registry, mas nenhuma arte usa.
5b. **Campo do config vazio aborta a geração.** Todo campo de `templates.config.ts` é obrigatório salvo `opcional: true`. Faltando qualquer um, `gerarProposta` lança `CamposFaltandoError` com a lista, a rota devolve 422 e nada é gravado no banco nem no Storage. Nunca pular campo vazio em silêncio: PDF com buraco onde deveria estar o nome do lead é pior do que PDF nenhum. Pela mesma razão, `resolverTemplateId` devolve `null` em vez de escolher uma arte padrão quando a idade falta.
6. Regerar PDF sobrescreve `{leadId}.pdf` no bucket `propostas` (URL estável para o link do WhatsApp). Preview no painel usa query param de cache-bust.
7. **O link público da proposta é `{APP_URL}/p/{slug}`** — 4 caracteres (707 mil combinações), coluna `slug` na tabela, gerada por `garantirSlug()` na primeira geração do PDF e nunca mais alterada (RF-14). Nunca devolver a URL crua do Supabase: esse link vai por WhatsApp e o lead lê o domínio. `APP_URL` errada em produção = link quebrado no celular de quem recebeu. A rota antiga `/proposta/{leadId}.pdf` continua viva porque links já enviados não podem morrer — mas não usar em código novo.
7b. **Os 4 caracteres são decisão consciente do owner (19/08/2026), não descuido.** O risco foi medido e apresentado: o espaço é varrível e um acerto expõe nome e data do evento. O owner manteve, pelo volume real (~3 leads/dia, trabalho artesanal que não escala) — nesse volume a colisão é desprezível e o espaço fica esparso. O que segura a porta é o **rate limit de 30/min por IP em `/p/[slug]`**: essa proteção não é opcional, é o que substitui o tamanho do slug. Nunca remover. Se um dia o volume mudar de ordem de grandeza, a correção é `TAMANHO_SLUG = 6` (594 milhões), e links antigos seguem valendo.

8. **A prévia da proposta e do contrato usa canvas paginado em todas as larguras** (`components/admin/PreviaProposta.tsx`, pdf.js). A correção de 20/10/2026 remove o iframe nativo, que deixava a prévia cinza no desktop e limitava a navegação no celular. A página aparece inteira, uma por vez, com paginação embaixo e o link "Abrir PDF em tela cheia" (mesma URL, `target=_blank`). Abaixo de 640px usa a largura disponível; no desktop a largura máxima é `min(672px, 70vh × 595/842)`, para a página A4 caber em até 70% da altura da janela. Não ampliar a página só pela largura do card: ela ficaria mais alta que a tela. O link externo preserva zoom/impressão do leitor do aparelho e permite ler o texto pequeno da miniatura. Falhas de carga ou desenho mostram mensagem e o link de abertura.
8b. O pdf.js entra por **import dinâmico** e só nessa tela: ele é grande e o bundle de `/formulario` é sagrado. Build `legacy` (já transpilado, roda em WebView antigo), e o arquivo é baixado com **um `fetch` só**, com os bytes entregues prontos ao `getDocument` — solto, o pdf.js fatia o PDF em vários range requests e `/p/{slug}` tem limite de 30/min por IP (7b).
8c. **O canvas acompanha a largura real da caixa com `ResizeObserver`**; o encaixe por altura no desktop é CSS responsivo. Ao trocar a URL depois de um erro, a caixa volta ao DOM e precisa ser medida/observada novamente: não manter o observer preso ao nó removido. Não escolher leitores diferentes por largura nem voltar a depender do leitor nativo dentro de iframe.

## Contrato: gotchas obrigatórios

Nasceu da leitura dos 17 contratos-cliente da Mel (de 03/2025 a 08/2026) e de uma revisão jurídica verificada, em 29/09/2026. Os contratos reais ficam em `contratos-passados/`, que está no `.gitignore` e **nunca** vai para o repositório: têm CPF, endereço e e-mail de clientes, e este repositório é público.

1. **Núcleo determinístico, IA confinada.** Qualificação das partes, valores, extenso, parcelas, datas, cláusulas-padrão, numeração e remissões saem de código testado (`montar.ts`, `clausulas.ts`). A IA (Claude Fable 5.1, `claude-fable-5-1`, em `lib/contrato/ia.ts`) faz três coisas e só: extrair os dados de quem assina de um texto colado pela Mel; redigir a cláusula "DAS CONDIÇÕES ESPECIAIS" a partir das observações; e revisar o contrato devolvendo AVISOS. Nunca reescreve cláusula-padrão. Motivo: em contrato de adesão, contradição entre um texto livre e o núcleo é lida contra quem redigiu (CC art. 423, CDC art. 47), e número inventado por modelo é justamente o erro que ninguém percebe na revisão.
2. **O texto da IA passa por `validarTextoIa` antes de entrar.** Todo número (valor, data, hora, percentual, dias) é conferido **com a unidade** ("10%" não se prova com "10 dias") contra o contrato SEM cabeçalhos "CLÁUSULA N", numeração de item e remissões (senão 1 a 16 estariam sempre "provados"), contra os dados estruturados e contra as observações. Número por extenso ("trezentos reais", "dez por cento") e data "10/12" ou "10 de dezembro de 2026" também são conferidos (se a Mel anotou a data sem o ano, vale o ano que o contrato já usa); dígito e extenso que não batem ("5 (duas)") e marcador repetido ("[CONTRATANTE] [CONTRATANTE]") são problema. A lista de vedados (`TRECHOS_VEDADOS`, cada item com o motivo em texto humano) barra arbitragem, "não se responsabiliza", ônus da prova, multa, juros, perda ou não devolução de valores, "de pleno direito", "independentemente de notificação", foro/comarca, reajuste, renúncia... Cláusula `origem: "ia"` com problema **bloqueia o PDF** até a Mel editar — editar é ela assumir o texto. Pedido que tem campo próprio (parcelamento, valor, local, pacote) volta como aviso "use a seção X", e não como cláusula: o campo gera o texto certo, a cláusula especial geraria uma segunda versão dele.
3. **A IA não recebe CPF, CNPJ, endereço, e-mail, telefone nem nomes** (contratante, representante, anuente, homenageado). `anonimizar.ts` troca por marcadores e desfaz na volta, comparando sem acento e sem caixa ("R. das Acacias", "ANA", "jd. primavera"), e antes disso varre QUALQUER e-mail, CPF, CNPJ e telefone, de quem quer que seja (o pai que paga, colado nas observações). Local de evento, making of ou ensaio que é espaço público vai inteiro (como a qualificação da CONTRATADA); o que tem dado pessoal ou diz de quem é a casa ("casa da Ana") passa pela troca. `dadosPessoaisNoTexto` confere o resultado com a mesma régua e, se algo sobrou, a IA não é chamada. Cada cláusula chega à IA com a origem no cabeçalho ("padrão aprovado", "redigida pela IA", "editada no painel"): no padrão aprovado a revisão só aponta o que depende DESTE contrato — estilo e lacuna genérica do modelo se repetiriam em todo contrato e esconderiam os avisos que importam. A extração é a única exceção, e é inevitável: ela recebe o texto que a Mel colou. Sem `ANTHROPIC_API_KEY` tudo funciona menos a IA — o contrato padrão sai, e as observações viram aviso "escreva a cláusula no editor". Falha da IA também não trava a Mel: a redação sai sem a cláusula especial, com aviso.
4. **Quem assina nunca é pré-preenchido com `respostas.nome` em evento de menor**: quem preencheu o formulário pode ser a própria debutante, e contrato assinado por menor de 16 é nulo (CC arts. 3º e 166). "Evento de menor" = debutante OU aniversário com idade < 18 — **nunca decidido pelo `TemplateId`**, porque `aniversario_adulto` cobre 15+ e inclui 15-17. Nesse caso a qualificação declara o vínculo (mãe, pai, responsável legal) e a autorização de imagem inclui o menor pela representação; com 16-17 anos o aniversariante entra como ANUENTE, assistido. O anuente também é o caminho para cobrir a imagem do outro noivo. **Empresa (PJ) não autoriza a imagem de ninguém**: fora do corporativo, contratante PJ gera aviso "atencao" pedindo o homenageado como anuente (em evento de menor, o responsável legal, que então autoriza a própria imagem e a do menor). O schema tem UM anuente: em casamento contratado por empresa, o aviso diz que o outro noivo segue sem autorização. `anuenteEhHomenageado` só olha o papel que COMEÇA pelo do homenageado — "pai do aniversariante" não é o aniversariante.
5. **Gênero gramatical é campo explícito escolhido pela Mel** ("Sra./Sr."), nunca inferido do nome, nem pela IA. 4 dos 17 contratos antigos erraram a concordância ("brasileiro, inscrita").
6. **O contrato é o único lugar do sistema em que preço vira número** (exceção à regra 6). O catálogo — `PACOTES` de `precos.ts` mais os adicionais de `catalogo.ts`, transcritos das artes — só PRÉ-PREENCHE; quem confirma o valor é a Mel. A tabela sugerida é a do ano do evento, mas ela pode escolher outra: proposta aceita antes do reajuste vale o preço da proposta (CDC art. 40 §2º), e dois contratos de 2027 foram assinados na tabela 2026. Dinheiro em centavos inteiros; o resíduo do arredondamento cai na última parcela; o extenso sai de `extenso.ts`, testado contra todos os valores dos contratos antigos.
7. **Decisões do owner sobre o texto (29/09/2026), não reabrir sem pedido:** SEM cláusula de arrependimento de 7 dias; SEM cláusula informativa de LGPD; COM reciprocidade (se a Mel faltar por culpa dela, devolve tudo mais o valor do sinal), COM ressalva de correção de erro da Mel sem custo, COM cláusula de acesso à conta do Instagram; foro PF = comarca do domicílio da CONTRATANTE, PJ = Monte Mor/SP; portfólio incluído na autorização de imagem, **inclusive anúncios pagos**. Corpo do PDF em 12 pt e negrito só nas frases limitativas e na autorização de imagem (CDC art. 54 §§3º e 4º) — negritar tudo anularia o destaque. **Pendentes com o owner, não implementar por conta própria** (mudam condição comercial): ressalva de caso fortuito/força maior na retenção do sinal (C05 do jurídico; hoje a desistência retém o sinal e devolve o que foi pago além dele), o que acontece com o saldo não pago no prazo (C14), prazo final da "finalização da cobertura" no tempo real, e a cláusula em que a empresa do corporativo responde pelas autorizações de imagem de convidados e funcionários (C20).
8. **Dados da CONTRATADA são constante** (`contratada.ts`), inclusive o endereço residencial da Mel — decisão do owner em 29/09/2026, sabendo que o repositório é público. Mudou endereço, e-mail ou PIX: muda ali, e só os contratos gerados dali em diante saem com o dado novo.
9. **Contrato é PII.** Tabela `contratos` com RLS, zero policies e revoke de anon/authenticated; bucket PRIVADO `contratos` (só PDF, até 10 MB). O PDF só sai por `/api/admin/leads/[id]/contrato/arquivo`, com sessão e `no-store` — nunca por `/p/{slug}`, nunca por URL do Storage. As colunas internas (`pdf_path`, `assinatura_token`, `posicoes_assinatura`, `assinado_path`, `trilha_path`) nunca vão ao navegador: o select do painel é explícito em `lib/supabase/contratos.ts`. Log com id e código, nunca CPF, e-mail ou payload.
10. **Excluir o lead apaga a pasta `{leadId}/` do bucket `contratos` ANTES da linha.** A linha de `contratos` cai por cascade; o arquivo não. Falha no Storage aborta a exclusão, pela mesma razão do PDF da proposta: "excluído" com o arquivo ainda no bucket é mentira.
11. **Assinatura pela API REST da Assinafy**, substituição autorizada pelo owner em 20/10/2026, atrás de `ProvedorAssinatura` (`lib/assinatura/`), com `ASSINATURA_DRY_RUN=1` como padrão de desenvolvimento. Novos envios usam `ASSINATURA_PROVEDOR=assinafy` (também o default). `ASSINAFY_API_KEY`, `ASSINAFY_ACCOUNT_ID` e `ASSINAFY_AMBIENTE=production|sandbox` são exclusivos do servidor. Fluxo `virtual`, verificação e notificação `Email`: preserva o PDF conferido, sem WhatsApp/SMS/biometria ou certificado A1/A3. Estimar antes do convite e recusar se houver custo extra ou falta de documento incluído no plano; a estimativa não reserva franquia contra envios concorrentes no painel da plataforma. Não comprar créditos nem mudar plano automaticamente. O envio continua sendo clique da Mel (regra 4). Tokens `assinafy-v1|...` prendem conta/ambiente/documento; persistir token antes do POST que notifica. Falha indeterminada mantém reserva, nunca repete convite. `certificated` é o único estado concluído: baixar e guardar `certificated` e `certificate-page` (certificado de assinatura real) antes de marcar assinado. A data de conclusão vem da atividade `document_ready`, nunca de `updated_at`. Consultar ao abrir e no botão existente; sem novo webhook. iLoveAPI fica apenas para consultas/cancelamentos/downloads de tokens legados e rollback explícito `ASSINATURA_PROVEDOR=ilovepdf`: preservar credenciais e arquivos antigos. Os 2.500 créditos grátis da iLoveAPI não cobrem assinatura. Instalar código não comprova ativação: verificar credenciais/ambiente e publicação. Operação em `docs/assinatura-assinafy.md`.
12. **O que foi para assinatura não muda.** Em `enviado` e `assinado` o texto trava (409 em salvar, redigir, editar e regerar). O PDF assinado e a trilha de auditoria ficam num caminho próprio de cada envio e nunca são sobrescritos — ao contrário da proposta (RF-14). Cancelar o envio, ou a plataforma devolver recusado/expirado, volta para `pdf_gerado`. Se a plataforma responde 404 no cancelamento E na consulta, ou o token gravado não se lê, "Cancelar envio" encerra o envio **só no sistema** (200 com `pedidoInexistente` e um `aviso` que a tela mostra no lugar do "Envio cancelado"); a consulta nesse caso responde 409 apontando o "Cancelar envio" e **não** destrava sozinha, porque roda ao abrir a página e encerrar envio é decisão da Mel. Contratante PJ vai à plataforma com o nome do REPRESENTANTE (quem assina de fato); a razão social fica só no bloco impresso.
12b. **Escrita que depende do que foi lido é guardada por `updated_at`** (`CondicaoEscrita.atualizadoEm`, em `_escrita.ts`): salvar texto editado, gravar o PDF, gravar a redação da IA e reservar o envio. Duas abas intercaladas deixavam `pdf_gerado` com o PDF de um texto e o painel mostrando outro — e o envio mandava o PDF velho. Conflito responde 409 "O contrato foi alterado em outra aba. Recarregue a página.", e editar o texto SEMPRE zera o PDF. No painel, link interno com alteração não salva pede confirmação por um listener de clique em captura: o App Router não dispara `beforeunload`.
13. **Contrato não mexe em `leads.status` nem em `enviado_em`**, que alimenta a cobrança de 7/30 dias. Com o contrato assinado, o painel oferece "Mover lead para Virou cliente", que usa o PATCH de status de sempre (e dispara o `VirouCliente` da regra 8b).
14. As rotas de IA têm `maxDuration = 300` e usam streaming: o Fable pode levar minutos. Redigir e revisar são duas requisições separadas, e cada uma cabe no teto sozinha. O prazo vai como `AbortSignal.timeout` nas opções do `stream` (250 s com 1 retentativa em redigir e revisar, 120 s com 2 na extração): o `timeout` do SDK só cobre até chegarem os cabeçalhos e deixava o corpo do stream sem limite nenhum. Estourado, vira `IaError` "timeout" e a redação sai sem a cláusula especial, com aviso.
15. `npm run contrato:verificar` (offline, sem banco e sem IA) monta e renderiza um cenário por arte × pacote, mais PJ, anuente, tempo real, 15/15/70, quitado etc., em `.contrato-verificacao/`, e falha com "{{", "undefined", numeração quebrada ou assinatura fora da página. Cada cenário pode exigir trechos do texto e avisos (`deveConter`, `naoDeveConter`, avisos esperados). `npm run e2e:contrato -- <base>` exercita a API contra o banco real, com admin e lead temporários que ele mesmo apaga. **Passe a base**: a porta 3000 desta máquina é de outro projeto. Só roda contra base local (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost`) sem `--permitir-remoto`, e quem diz se a assinatura está em dry run é o SERVIDOR (`assinaturaDryRun` no GET do contrato), nunca o `.env` de quem roda o script: fora do dry run o envio não roda e o script termina vermelho.
16. **O escopo sabe QUANTO TEMPO o auxiliar trabalha** (`escopoEfetivo(servico, templateId)` → `minutosAuxiliar`). Storymaker por evento é equipe de dois a cobertura inteira; por hora, só vira equipe de dois se as horas cobrirem a cobertura — antes disso objeto, serviços e alimentação dizem "por até N horas". O parágrafo dos making ofs "impossibilitando a realização simultânea" só entra se nenhum adicional indicar segunda pessoa (inclusive o livre que fala em storymaker, auxiliar ou simultâneo), com aviso para conferir a logística. A unidade de cobrança (`unidadeDoAdicional`) é UMA função, da montagem, que o painel reusa: o campo de horas aparece exatamente onde o contrato diz "por hora".
17. **Ensaio fotográfico (Pacote Luxo da debutante) tem data, local e horário próprios** (`evento.ensaioData/ensaioLocal/ensaioHorario`, vazio = A DEFINIR, com agendamento de comum acordo e 10 dias de antecedência). Acontece ANTES do evento (depois é faltante; o mesmo dia é aceito), e o "Tempo de serviço no dia do evento" não soma o ensaio. O corporativo é entrega em tempo real nos três pacotes (a arte promete stories durante o evento), o que traz a cláusula das condições técnicas.
18. **Pagamento tem quatro opções e quase nenhum campo** (pedido do owner em 30/09/2026): "30% + 70%" (o padrão das artes), "Metade-metade" (50% de sinal na assinatura + 50% até 10 dias antes do evento), "Já pago" e "Personalizado". ### Identidade visual do SITE (não do PDF)

**As duas identidades são separadas e não se contaminam.** O site tem a paleta abaixo; o PDF tem a arte do Figma, com as cores e fontes que a Mel desenhou lá. Unificar as duas seria destruir a arte — nunca mexer em `assets/templates/` ou nas cores de `lib/pdf/templates.config.ts` a pretexto de "seguir a paleta".

- **Paleta: duas cores.** O escuro da marca (`#20130A`) e `#F1F1F1`, em `--marca-escuro` e `--marca-claro`. Branco entra só como superfície de card. Tom intermediário se deriva com opacidade (`rgb(var(--marca-escuro-rgb) / 12%)`), nunca acrescentando um hex novo — por isso existe `--marca-escuro-rgb`, os componentes soltos da mesma tinta.
- **A identidade da Mel (Figma, frame `7120:556`) tem quatro tons**: `#20130A` (escuro, e a cor do logo), `#4D2B22`, `#823B25` (terracota) e `#CBAD95` (areia), mais um creme `#F0E0C7`. O app usa **dois**: o escuro e `#F1F1F1`. A terracota entra num lugar só, o **anel de foco** (`--ring`) — é o acento da marca onde ele aparece em toda tela sem repintar nada. Os outros dois ficam registrados no comentário do `globals.css` para ninguém inventar um marrom diferente; não estão em uso.
- **O claro continua `#F1F1F1`, e não o creme da marca.** Troca pedida pelo owner em 29/08/2026 foi só das cores **escuras** (preto → `#20130A`), para o painel seguir clean. Trocar o fundo pelo creme é decisão nova, não consequência desta.
- **`--muted-foreground` é 65%, não 60%.** O marrom é mais claro que o preto: a 60% caía para 4,56:1 sobre `#F1F1F1` — passa no AA, mas sem folga. A 65% dá 5,37:1. Ao mexer na tinta escura, refaça essa conta.
- **O logo é `components/marca/LogoMel.tsx`**, SVG inline com `fill="currentColor"` (o arquivo original vinha com `#20130A` fixo). Inline e não `<img>`: aparece no cabeçalho de toda tela autenticada, e uma requisição a mais atrasaria a primeira pintura. Altura por classe (`h-7` = 28px), largura automática pelo viewBox 274x38.
- **A regra das duas cores vale para as telas do LEAD** (`/formulario`, `/p/[slug]`, `/`). **Exceção: a LP de venda `/casamento` usa a identidade COMPLETA** (escuro, `#4D2B22`, terracota, areia `#CBAD95` e creme `#F0E0C7`), decisão do owner em 01/10/2026 — página de venda pede o calor da marca. Os três tons extras vivem em `.lp-casamento` (`globals.css`), não no `:root`: fora da LP, `bg-marca-creme` não pinta nada. O `estilo:verificar` aplica a paleta POR URL: ampla em `/casamento`, estrita nas outras. Nas faixas escuras da LP o anel de foco vira creme (`.lp-escuro`), porque terracota sobre o escuro fica a 2,2:1. O **painel interno** usa também as cores de status do quadro — slate/âmbar/sky/emerald —, definidas só em `CLASSE_STATUS`/`TEMA_COLUNA` (`lib/admin/rotulos.ts`). Decisão do owner em 20/08/2026, ao pedir o kanban com "visual Notion". Já havia precedente não documentado (`emerald-100` no badge de enviado, `amber-50`/`emerald-50` nos avisos do detalhe). As classes são **literais**: `bg-${cor}-50` some do CSS porque o scanner do Tailwind v4 não lê string interpolada. E **não** apontar `estilo:verificar` para `/admin` — ele falharia por desenho, além de exigir sessão.
- **Favicon e ícone da tela de início do iPhone são o MESMO desenho** (`lib/marca/icone.tsx`, aprovado pelo owner em 06/10/2026): o monograma MS (o símbolo do logo, `lib/marca/monograma.ts`) em creme `#F0E0C7` sobre o escuro `#20130A`, ocupando 60% da altura. `app/icon.tsx` (64 px) e `app/apple-icon.tsx` (180 px) só mudam o tamanho, e o Next gera o `<link rel="apple-touch-icon">` sozinho. Quadrado cheio, sem canto arredondado e sem transparência: o iOS aplica a própria máscara e pinta de preto o que for transparente. O `icone.test.ts` confere tamanho e canto opaco dos dois.

Campo de texto (inclusive data e hora) fica com o cursor de digitação — ali a mão sugeriria botão. A regra é global, em `@layer base`; nunca reintroduzir `cursor-default` num componente (o utilitário vence a camada base e foi o que o shadcn trouxe por padrão). Motivo de existir: o **Tailwind v4 mudou o padrão do `button` de `pointer` para `default`**, então sem a regra o sistema inteiro perde a dica de clicabilidade.
- **Raio: 6px em tudo.** Toda a escala `--radius-sm..4xl` aponta para `--radius`. Não usar `rounded-full`: mudar o raio do app inteiro deve ser mexer em uma linha só.
- `npm run estilo:verificar` (com `npm run dev` em outro terminal) checa cinco coisas no DOM renderizado: raio, fonte, paleta, **cursor de todo clicável** e ausência de scroll horizontal em 360px. Julgar por screenshot não serve — 6px num print em 2x parece 12px.
- **O verificador não clica**: do formulário (uma SPA) ele só enxerga a PRIMEIRA tela de cada URL. (Desde que `/orcamento` existe, a tela de categoria é a primeira de uma URL e entra na checagem.) Foi assim que `border-foreground/25` (no `OpcaoEscolha`, tela de categoria) conviveu meses sem ser checado e só acusou quando a mesma classe chegou à abertura. E o que ele acusou não era cor nova: os modificadores de opacidade do Tailwind v4 (`/25`, `/70`) compilam para `color-mix(in oklab, ...)`, então o `getComputedStyle` devolve `oklab(...)` e não `rgba(...)`. O script compara os tons da marca também em oklab, por valor e com tolerância. Os tons ficam numa tabela só (`TOM`, com hex, rgb e oklab) e `paletaDaUrl` escolhe quais valem em cada página: ao acrescentar um tom, ponha as três notações ali. Ele também rola a página até o fim antes de inspecionar (conteúdo montado por IntersectionObserver), e inspeciona elemento com `visibility: hidden` — por isso o visualizador de Reels e a barra fixa da LP ficam sempre montados.
- `chrome --headless --window-size=360,x` **não** dá viewport de 360px (o Chrome tem largura mínima de janela e a imagem sai só recortada, simulando um estouro que não existe). Use `npm run screenshot -- <url> <saida.png> 360`, que emula via CDP.

### Persistência e validação do formulário

- A criação inicial gera `tentativa_id` antes do POST e conserva sua identidade/payload até confirmar o ACK. A tentativa e a intenção local posterior ficam em chave própria; recarga recupera o mesmo UUID e GET 404 transitório repete o POST com o mesmo ID. Nunca gerar outro UUID por erro de rede. A PK existente escolhe o INSERT vencedor: só `23505` com esse ID recupera o snapshot atual, sem upsert, sobrescrita ou novos efeitos. HTTP 201 é nascimento; GET/POST 200 são recuperação e não disparam novo Pixel Lead. Clientes anteriores sem `tentativa_id` mantêm compatibilidade. Perda do ACK entre banco e servidor não certifica entrega CAPI; esse lado continua best-effort.
- O autosave usa uma fila por lead: um PATCH ativo e somente o conjunto mais recente de respostas pendentes. O avanço continua otimista; o submit aguarda a confirmação de todas as pendências. Reconexão e retorno à aba tentam salvar novamente, sem repetir automaticamente conflitos ou dados inválidos.
- A resposta confirmada pelo servidor é a `base` do próximo PATCH e do submit: categoria, respostas e passo atual. PATCH com `base` exige um snapshot completo e substitui as respostas; mesclar o snapshot com o banco recuperaria respostas apagadas em uma troca A→B→A de categoria. O servidor compara esses campos antes de escrever e condiciona o UPDATE por ID, status e `updated_at` lido internamente. Nunca colocar o JSON inteiro das respostas no filtro da URL: texto longo aceito pelo formulário excede limites de transporte. `updated_at` não é versão das respostas do navegador, porque gravar rastreio também altera esse timestamp: zero linhas exige releitura e comparação de categoria/respostas/passo; só repetir se o mesmo snapshot continua incompleto. São até três tentativas; alteração de respostas retorna conflito, atualização contínua de metadados retorna falha recuperável. Erro de escrita não é repetido às cegas. Clientes anteriores sem `base` mantêm compatibilidade, com proteção contra mudanças durante a leitura/escrita, sem detectar um snapshot já antigo antes da primeira leitura.
- Apenas o submit que de fato muda `incompleto` para `aguardando_revisao` agenda a notificação da Mel e o `SubmitApplication`. Zero linhas alteradas não é uma nova conclusão; repetição retorna o estado já fechado sem repetir efeitos.
- Rascunho pendente pertence ao mesmo UUID e fica separado do identificador de retomada. Há um slot persistido por UUID em cada navegador, compartilhado entre abas: ele guarda o último snapshot local, sem histórico independente por aba. Só é removido após confirmação do snapshot correspondente; concluir em uma aba preserva um rascunho divergente já salvo pela outra. Armazenamento bloqueado nunca transforma um POST confirmado em falha nem apaga o UUID mantido em memória.
- O mínimo de data e a validação usam o dia de `America/Sao_Paulo`, independentemente do fuso do servidor ou do aparelho. A função pura compartilhada fica fora do catálogo de contratos para não aumentar o bundle do formulário.
- Validação de integração usa banco, Storage e credenciais fictícios em ambiente isolado. `MAIL_DRY_RUN=1` impede SMTP, mas não impede alterações no banco de produção; localhost, sozinho, também não é isolamento.
